The **roaming WireGuard endpoint** (`delta-vpn.zero-five.space`) is a Cloudflare
A record (grey cloud / proxied=false) that resolves to the **home public IP**
(46.162.95.145 as of 2026-08). Roaming peers (MacBook, iPhone) use
`Endpoint = delta-vpn.zero-five.space:51820` to reach Delta from outside.

Home/ISP connections are rarely static, so if the ISP reassigns that IP and the
record goes stale, roaming devices can't find Delta. This page documents the
**DDNS updater** on Delta that keeps that record current automatically.

Deployed + verified 2026-08-23.

## Why not an outbound IP-echo

The usual DDNS trick — ask the internet "what's my IP?" (`api.ipify.org`,
`ifconfig.me`, …) — **does not work here**: Delta's `wg-quick@mullvad` is
`active` (full-tunnel `0.0.0.0/0`), so outbound traffic egresses through a
Mullvad exit (e.g. `45.130.200.131`), **not** the home WAN IP. The updater must
learn the home WAN IP from **inside** the LAN instead.

## The WAN-IP source: UPnP-free via alpha UDP echo (2026-08-23)

**The old UPnP IGD source was replaced.** UPnP is the exact feature that tears
out manual port-forwards (the 2026-08-23 Minecraft incident destroyed the router's
manual forwards and the router UI's :5500 IGD surface). The DDNS now detects the
home WAN with **no UPnP**:

1. **Alpha** runs a tiny UDP echo service on `:51823` (`udp-echo-518.py`,
   systemd `zero-five-udp-echo.service`) that replies with the source IP it
   observes. Deployed on alpha, UFW-allow UDP 51823.
2. **Delta** sends one UDP datagram to `95.111.229.142:51823` (alpha). A
   **destination-based policy route** (`ip rule add pref 5 from all to
   95.111.229.142 lookup main`) forces that probe **outside** the Mullvad tunnel,
   egressing via the home router — so alpha sees Delta's **home WAN IP**, not a
   Mullvad exit.
3. The echo reply IS the home WAN IP. Credential-free, no router UPnP.

**Self-healing rule:** the DDNS script runs as root (systemd `User=root`) and
re-adds the `lookup main` bypass on every run (`ensure_bypass_rule()`), so it
survives tunnel restarts/reboots with no manual `mullvad.conf` edit.

**Verification:** `python3 zero-five-ddns.py --wan-only` returns
`home WAN IP: 46.162.95.145` (the home WAN, NOT the Mullvad exit `45.130.200.131`).

## Mullvad full-tunnel leak — bypass raised to pref 5 (2026-08-24)

**Symptom:** the CF record briefly pointed at `45.130.200.131` (the Mullvad
exit IP), breaking roaming peers and the Minecraft CNAME. Root cause: the
bypass rule was `pref 100`, the **same priority** as the `mullvad.conf` PostUp
exemption — and when Mullvad's rules won the tie, the probe rode the full
tunnel (`AllowedIPs 0.0.0.0/0`) and alpha saw the Mullvad exit, not the home
WAN.

**Fix (committed `zero-five-infra` `45d2a30`):**
- `BYPASS_RULE` raised `pref 100` → **`pref 5`** — always beats Mullvad's
  `pref 100` rules, so the probe and delta's mesh WG egress via the real WAN.
- `mullvad.conf` PostUp/PostDown exemption corrected `sport 51821` (stale) →
  **`sport 51820`** (delta's actual WG listen port). Backup:
  `/etc/wireguard/mullvad.conf.bak-20260824`.

**Diagnostic tell:** in alpha's `wg show wg0`, delta and MSI egress from the
home WAN IP while gamma and beta (the Mullvad-gateway clients) egress from the
Mullvad exit. If the DDNS record ever equals the gamma/beta egress IP, the
probe is leaking through Mullvad again — check `ip rule show` for the pref-5
entry.

## Layout

- Script: `~/services/zero-five-infra/scripts/zero-five-ddns.py` (on Delta,
  pulled from git). Secret-free — the Cloudflare token is read at runtime from
  `/etc/letsencrypt/cloudflare.ini` (the same Zone:DNS:Edit token certbot
  uses). Filename/ini key: `dns_cloudflare_api_token`.
- **Alpha UDP echo**: `~/services/zero-five-infra/scripts/udp-echo-518.py`
  (on alpha, systemd `zero-five-udp-echo.service`, binds `:51823`, replies with
  the observed source IP). UFW-allow UDP 51823.
- Systemd units (from `systemd/zero-five-ddns.*.example`):
  - `/etc/systemd/system/zero-five-ddns.service` — oneshot root run of the
    script.
  - `/etc/systemd/system/zero-five-ddns.timer` — every 15 min
    (`OnUnitActiveSec=15min`), first check `OnBootSec=2min`, `Persistent=true`
    so it catches up after downtime. `systemctl enable zero-five-ddns.timer`.
- State: `/var/lib/zero-five-ddns/last-run.json` (WAN IP + timestamp + whether
  it changed), which also makes the run idempotent — if no WAN change, no
  Cloudflare call.

## How it updates Cloudflare

1. Read the home WAN IP via the alpha UDP echo (UPnP-free).
2. `GET` the `delta-vpn.zero-five.space` A record (zone `zero-five.space`).
3. If the WAN IP **differs** from the record, `PATCH` it (name + type + content
   + `proxied:false` + `ttl:1`). If unchanged, do nothing.
4. Write the state file.

It **only ever touches the `delta-vpn` A record** — never other records, never
proxied/Cloudflare-ORANGE settings (orange-cloud would break WireGuard speed).
It is idempotent and cheap (one GET per 15 min when nothing changes).

## Install (one-time)

On Delta (needs sudo — it writes to `/etc/systemd/system/` and reads the
root-only token once for a first-run check):

```bash
sudo bash ~/services/zero-five-infra/scripts/install-zero-five-ddns.sh
```

The script copies the `.example` units to `/etc/systemd/system/zero-five-ddns.{service,timer}`,
`systemctl enable zero-five-ddns.timer`, and runs one first check (which is a
no-op if the WAN IP is already correct).

## Verify (from alpha, no sudo — SSH to Delta as `manuel` + docker via the hub)

Prints: Delta's home-WAN-IP (token-free `--wan-only`, via the alpha UDP echo),

## Manual / emergency

- `python3 zero-five-ddns.py --dry-run` — report what it would do.
- `python3 zero-five-ddns.py --force-update-to <IP>` — force the record to an
  explicit IP (e.g. recover from a bad run). Validates IPv4.
- `--probe HOST:PORT` — override the alpha UDP echo target (default
  `95.111.229.142:51823`).
- Rollback: `sudo systemctl disable zero-five-ddns.timer`, delete
  `/etc/systemd/system/zero-five-ddns.{service,timer}`. The CF record just
  stays at the last value; nothing breaks (it's only a WAN-IP registry).

## Failure modes

| Symptom | Cause | Fix |
| --- | --- | --- |
| `WAN IP detection failed: could not determine home WAN IP via UDP echo` | Alpha echo :51823 down, or the `lookup main` bypass route missing (Mullvad exit report) | Confirm `zero-five-udp-echo.service` active on alpha + UFW allows UDP 51823; the script self-adds the bypass — check `ip route get 95.111.229.142` shows eth0/192.168.1.1, not `dev mullvad` |
| `Permission denied: /etc/letsencrypt/cloudflare.ini` in a non-root run | Only root reads the token | Run the script under the systemd service (root), or `--wan-ip` for a token-free check |
| Record goes stale but the timer is enabled | Probe timeout (alpha echo down) or the bypass route missing after a restart | `ensure_bypass_rule()` re-adds it on the next run; if alpha is up and still stale, check `ip rule list` for the `to 95.111.229.142 lookup main` entry |
| Roaming unreachable at a new location | Firewall/router UDP 51820 forwarding may not follow a WAN IP change | On a network change, verify port 51820 is still forwarded (check manually) |

> **The firewall drop that broke roaming (2026-08-23, fixed):** Delta's gateway
> `forward` chain has `policy drop` and only accepted `br-*` (Docker container)
> egress to mullvad/eth0. An inbound WAN WireGuard handshake (public source IP)
> destined `10.40.0.2:51820` matched no accept → dropped *before* reaching
> WireGuard. Fix: `sudo nft add rule ip gateway forward udp dport 51820 accept`
> (accept only the WG port; no general egress opened). The mesh always worked
> because it rides the `wg0` tunnel interface, which never crosses the forward
> chain — the mesh-works-WAN-doesn't asymmetry is the signature of this drop.

## Design notes / trade-offs

- **UDP-echo instead of outbound-echo** — required here because of the Mullvad
  full-tunnel; the destination `lookup main` bypass makes alpha the one oracle
  that sees the home WAN. Trade-off: requires the alpha UDP echo service to be
  up and the bypass route present (both self-healed every run).
- **No router UPnP** — the previous UPnP IGD source was dropped because UPnP
  is the thing that tears out static forwards; the UDP echo needs no router
  cooperation and cannot disturb other config.
- **Timer, not a loop** — systemd timers are the established Zero Five pattern
  (backup, certbot). `Persistent=true` means missed ticks (laptop asleep,
  Delta reboot) are still followed at the next scheduled check.
- **Token reuse** — the certbot `cloudflare.ini` token already has
  `Zone:DNS:Edit`; no new secret. Critical: the *token must stay root-only*
  (`0600`); the repo script reads it at runtime, never embeds it.
- **Only one record** — deliberately narrow blast radius (`delta-vpn` A
  record). The mesh renumber does not affect it (it points at the home WAN IP,
  not Delta's mesh address).

## Roster / mesh context

The DDNS record is independent of the WireGuard mesh renumbering currently in
flight — it holds the **home WAN IP**, so Delta moving mesh addresses doesn't
change what `delta-vpn` should point at. The roaming peer configs
(`Endpoint = delta-vpn...:51820`) use this record on MacBook/iPhone.

The Raspberry Pi is **Delta**, the always-on home control node. It
will sit beside Alpha logically: Alpha remains the public WireGuard hub, while
Delta owns LAN-facing services that must remain available when laptops are
asleep.

## Identity

| Property | Planned value |
| --- | --- |
| Hostname | `delta` |
| LAN role | Always-on home services and backup controller |
| WireGuard address | `10.8.0.2/32` |
| LAN address | `192.168.1.106` (static/reserved by owner) |
| Private DNS zone | `home.zero-five.space` |
| VPN DNS name | `delta.home.zero-five.space` |

The Pi's WireGuard address is deliberately `.2`: it is infrastructure, not a
personal client or VM. The private key stays on Delta; the Alpha peer contains
only its public key and `/32` route.

Delta now also contains direct backup peer definitions for the registered
WireGuard nodes. Their observed NAT endpoints are operational hints, not fixed
addresses; a peer must receive Delta's public key before the direct handshake
can succeed. Alpha remains the working path until those reciprocal peer blocks
are applied.

Use the fixed LAN address for direct SSH; this does not traverse Alpha:

```bash
ssh delta
```

The tracked client model is
`zero-five-infra/wireguard/delta.conf.example`; the tracked SSH fragment is
`zero-five-infra/ssh/macbook-zero-five.config.example`. `delta` resolves to
`192.168.1.106` and has no `ProxyJump`. The WireGuard address is used for
private VPN services and routes, not for this direct LAN administration path.

## Delta WireGuard deployment

On Delta, install WireGuard, generate its identity, and keep the private key
only in `/etc/wireguard/wg0.conf`:

```bash
sudo apt update
sudo apt install -y wireguard
sudo install -d -m 700 /etc/wireguard
umask 077
wg genkey | sudo tee /etc/wireguard/delta.key >/dev/null
sudo cat /etc/wireguard/delta.key | wg pubkey
```

Register the displayed public key as the Delta peer on Alpha, then create the
client configuration from the tracked example with the generated private key.
Delta's public SSH key is also authorized on Alpha's `manuel` account:

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIDftmaFI4C+2JMVW52g+LW3oVxMymuz3I9QIy5LWofNK manuel@delta
```
Validate it before activation:

```bash
sudo wg-quick strip wg0
sudo systemctl enable --now wg-quick@wg0
sudo wg show
ping -c 3 10.8.0.1
```

Do not restrict Delta's LAN SSH path until `ssh delta` succeeds from a second
terminal. Keep the LAN session and physical console available during the first
activation.

## Responsibilities

### Wake-on-LAN relay

Delta can wake the LAN machines because a sleeping host cannot receive a
WireGuard packet. The tracked source is
`zero-five-infra/scripts/delta-wake`; install it on Delta as
`/usr/local/bin/delta-wake`:

```bash
sudo install -o root -g root -m 0755 /home/manuel/delta-wake /usr/local/bin/delta-wake
```

Commands:

```bash
delta-wake gamma
delta-wake beta
```

The command sends a UDP magic packet to `192.168.1.255:9` using the wired MAC
addresses recorded in the [Gamma Wake-on-LAN runbook](/docs/laptop-gamma/wake-on-lan)
and [Beta Wake-on-LAN runbook](/docs/laptop-beta/wake-on-lan). It requires Delta
to be awake and connected to the home LAN. It cannot wake a machine whose
firmware does not preserve Wake-on-LAN after full shutdown.

### Private DNS

Delta will answer private names for VPN and LAN clients, for example:

```text
delta.home.zero-five.space       10.8.0.2
gamma.home.zero-five.space       10.8.0.3
beta.home.zero-five.space        10.8.0.4
blackarch.home.zero-five.space   10.8.0.100
```

The DNS service must listen only on the LAN and WireGuard interfaces. It must
not become a public resolver. The first implementation should use one small,
well-supported DNS service; do not add a DNS dashboard until the records need
frequent owner editing.

### Home control

Delta is the control point for:

- Wake-on-LAN for Gamma and Beta;
- smart plugs and lamps;
- later house sensors and automations.

WOL commands must target the LAN broadcast domain, not the sleeping machines'
WireGuard addresses. Smart-home devices remain on the LAN and are controlled
from Delta; their credentials belong in a runtime-only secret store, never in
the handbook or `zero-five-infra`.

Do not expose the control API or smart-device protocols to the public internet.
Remote control enters through WireGuard and is authorized separately from DNS.

### Backups

Delta will orchestrate backups, but the Pi's SD card is not a backup target.
The first backup design must include an external disk or future NAS, with:

- encrypted or access-controlled storage;
- pull-based jobs where practical, so a compromised source cannot erase every
  backup;
- retention and pruning rules;
- periodic restore tests;
- monitoring for failed, stale, or full backups.

The exact tool and storage layout remain open until the external disk/NAS is
chosen. Do not install a backup stack speculatively.

## Migration gate

Delta's LAN address is now `192.168.1.106`; existing peers keep their current
WireGuard addresses until each migration is separately verified.

Migrate in this order:

1. Install Delta on the LAN and reserve `192.168.1.106`.
2. Add Delta as the Alpha peer at `10.8.0.2`.
3. Deploy private DNS and verify records from Alpha and one VPN client.
4. Move Gamma, Beta, MacBook, MSI, and iPhone one at a time, updating both
   runtime and persistent Alpha state.
5. Move BlackArch from `10.8.0.101` to `10.8.0.100`.
6. Update SSH aliases, Ollama binding, firewall rules, QR templates, and all
   handbook/infra references.
7. Reboot-test every migrated peer before removing old routes.

Keep the current working configuration and physical/LAN recovery paths until
the final peer has passed handshake, DNS, SSH, and reboot checks.

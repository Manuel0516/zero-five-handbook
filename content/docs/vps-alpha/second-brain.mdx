[Second Brain](https://github.com/Manuel0516/second-brain) is a private, self-hosted life OS — calendar, notes, finances, fitness, food, and AI-assisted capture. Live at **[brain.zero-five.space](https://brain.zero-five.space)**, deployed at `~/services/second-brain`.

## Stack

Four containers, Compose project `secondbrain` (`compose.yaml`):

| Service | Image | Role | Network exposure |
|---------|-------|------|------------------|
| `web` | built — nginx + React (Vite) | Frontend, proxies `/api` | `traefik` network → HTTPS |
| `api` | built — FastAPI (Python 3.13, uv) | Backend | internal + egress only |
| `db` | `postgres:18.3-alpine` | Database | internal only |
| `minio` | `quay.io/minio/minio` | Object storage (files, images) | internal only |

Network design is strict: `internal` is a Docker **internal** network (no outbound), only `api` also joins `egress` (it needs outbound HTTPS for Google Calendar / ICS sync and OpenRouter), and only `web` joins the external `traefik` network. The database and MinIO can never reach or be reached from the internet.

The web container also carries `hub.*` labels, so it appears on the [Hub dashboard](/docs/vps-alpha/hub) as an admin-only card (🧠).

## Configuration

`.env` on the server (documented by the committed `.env.example`). Key variables:

| Group | Variables |
|-------|-----------|
| Database | `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` |
| Object storage | `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` |
| Auth | `JWT_SECRET_KEY`, access/refresh expiry, `TOTP_ENCRYPTION_KEY`, login rate limits |
| Initial user | `INITIAL_USER_USERNAME` / `EMAIL` / `PASSWORD` |
| Google Calendar | `GOOGLE_CLIENT_ID` / `SECRET` / `REDIRECT_URI` / `TOKEN_ENCRYPTION_KEY`, `CALENDAR_SYNC_INTERVAL_MINUTES` |
| AI capture | `OPENROUTER_API_KEY`, `OPENROUTER_MODEL` (default `google/gemini-2.5-flash`) |

> **Note:** Unlike the rest of the AI stack, second-brain's AI features call **OpenRouter** (cloud), not the local Ollama.

## Embedded AI agent (2026-08)

An autonomous assistant lives **inside the API** — a ReAct loop that calls the app's own REST endpoints as tools (the "tools are 1:1 with existing endpoints" pattern). Live on `development`, planned in `docs/work/plans/embedded-agent/` (repo) with the product spec `docs/product/AI_ASSISTANT_MODULE.md`.

**What it does**

- Model: `deepseek/deepseek-v4-flash` via OpenRouter (raw httpx, zero new deps), configurable per-user via `AISettings` (provider/model/autonomy — v1 only `ask_before_write`).
- Read tools: search/get pages, events, food logs/summary, fitness overview, exercises, `get_today`, `get_app_summary`.
- Write tools (create/update/delete pages, events, links, food logs, workout sessions) are **proposed, never executed**: the loop pauses, the UI shows a preview card, the user confirms or rejects; the loop resumes only when all pending actions of that turn are resolved (`confirm`/`reject` endpoints; `undo` restores via a stored pre-image).
- Hermes-style self-improvement: `remember(fact)` (durable memory injected into every system prompt) and `save_skill/load_skill/list_skills` (markdown procedures the agent writes and reuses).
- Chat is SSE (`POST /api/ai/conversations/{id}/messages` → `text/event-stream`): `conversation`, `text_delta`, `tool_call`, `tool_result`, `confirm_required`, `message_done`, `error`, `done`. The frontend panel (floating button → slide-over, `apps/web/src/modules/assistant/`) renders streams, tool chips, and confirmation cards.
- Tools execute by calling the API itself over localhost with a server-minted JWT (auth via the existing `access_token` cookie flow — `get_current_user` does not read bearer headers); base URL configurable via `AI_INTERNAL_API_URL`.

**Data model** (one Alembic migration `ai_assistant_module`): `AIConversation`, `AIMessage`, `AISettings`, `AIMemory`, `AISkill`, `AIAction` — all `user_id`-scoped.

**Pre-existing bugs fixed along the way** (deployed code): `/api/pages/search` and `/api/fitness/stats/overview` were shadowed by parameterized routes (`{page_id}`, `exercise/{exercise_id}`) → moved static routes first.

## Telegram bot (2026-08)

The agent is also reachable as a Telegram bot (**@Zero_Five_bot**, "Hermes-Life") via a
zero-dependency bridge in `apps/bot/` — a stdlib-only Python long-polling loop that logs
into the API (cookie auth with the initial-user credentials), forwards chat messages to
the SSE agent endpoint, streams the reply, and renders write confirmations as inline
keyboards (✅ Apply / ✖ Reject; undo via callback). One long-lived conversation per chat;
`/new` starts a fresh one. Chat-to-conversation mapping persists in the `bot-data` volume.

Env: `TELEGRAM_BOT_TOKEN` (required), `TELEGRAM_ALLOWED_USERS` (default `1110963147`).
The bot joins `internal` (API) + `egress` (Telegram) networks and waits for a healthy API.

## CI/CD

Two GitHub Actions workflows:

1. **CI** (`ci.yml`) — on every push/PR: Node 24 + uv, `npm run check` (frontend format/lint/types/tests/build + backend format/lint/types/tests), and validates the production compose config.
2. **Deploy** (`deploy.yml`) — runs only after CI **succeeds** on `main`
   (`workflow_run` trigger, `production` environment, concurrency-locked). Its
   SSH key is restricted to a forced server-side deploy procedure. The
   dispatcher accepts only a validated 40-character commit SHA, and the fixed
   procedure redeploys that exact tested revision; workflow text cannot become
   an arbitrary remote shell program.

Manual deploy:

```bash
cd ~/services/second-brain && git pull && docker compose up -d --build web api
```

## Setup from scratch

```bash
cd ~/services
git clone git@github.com:Manuel0516/second-brain.git && cd second-brain
cp .env.example .env && vim .env      # every :?-marked variable is required
docker compose up -d --build
```

The API creates the initial user from the `INITIAL_USER_*` variables on first boot. Traefik picks up the `web` container automatically (`brain.zero-five.space`).

## Data and backups

| Volume | Contents |
|--------|----------|
| `secondbrain_postgres-data` | All structured data |
| `secondbrain_minio-data` | Uploaded files/objects |

```bash
# Postgres dump without stopping the stack
docker exec secondbrain-db-1 pg_dump -U secondbrain secondbrain | gzip > ~/backups/secondbrain-$(date +%F).sql.gz
```

This creates only a local staging dump. It becomes a backup after the planned
Raspberry Pi retrieves an encrypted copy, retains versions, and a PostgreSQL
restore is tested. MinIO objects require a separate consistent export; the SQL
dump does not contain them.

## Development

Local development happens on the MacBook/laptop, not the VPS — see the repo README: Vite dev server on `:5173` proxying to FastAPI on `:8000`, with only `db` and `minio` in Docker (`compose.dev.yaml`). The repo also defines the multi-agent workflow (`AGENTS.md`, Ponytail plugin for Claude Code/Codex).

**VPS dev environment (used for the embedded-agent work, 2026-08):** the VPS can also run a full dev stack without touching prod — `docker compose -f compose.dev.yaml up -d` (project `secondbrain-dev`, Postgres on `127.0.0.1:5433`, MinIO on `127.0.0.1:9100`), then the API and web run directly on the host: `uvicorn app.main:app --reload --port 8000` (from `apps/api`, env from `.env.dev`) and `npm run dev -- --port 5173` (from `apps/web`). Everything binds to `127.0.0.1` only; prod containers are untouched. Dev login: `manuel@dev.zero-five.space` (credentials in the VPS-only `.env.dev`). Feature branches are developed in git worktrees (`~/worktrees/sb-*`) and merged into `development`; prod deploys from `main` only (see CI/CD).

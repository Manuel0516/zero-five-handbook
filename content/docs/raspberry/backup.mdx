## Current scope

The first implementation is an emergency safety net, not a fully tested
disaster-recovery system. It has one destination, Delta's external disk at
`/srv/nas`, and does not yet include restore drills or a second copy.

Minecraft is explicitly excluded.

The daily job runs at 21:00 in Delta's local timezone. It backs up Delta,
Alpha, Beta, and Gamma sequentially.

## Wake/suspend — restore prior power state

Beta and Gamma are laptops that normally sleep. The controller restores their
prior power state around their backup:

- if a source was **asleep**, it is woken with a Wake-on-LAN magic packet
  (`delta-wake`), the backup runs, then it is suspended again;
- if a source was already **awake**, the backup runs and it is left running.

Alpha is the always-on VPS and is never woken or suspended. A source with no
suspend command configured is simply left running after its backup.

The wake timeout, WoL target names, and suspend commands are configuration in
`backup.env`:

| Variable | Value on Delta |
|---|---|
| `WAKE_SCRIPT` | `/home/manuel/services/zero-five-infra/scripts/delta-wake` |
| `WAIT_UP_S` | `180` |
| `BETA_WAKE_NAME` / `GAMMA_WAKE_NAME` | `beta` / `gamma` |
| `BETA_SUSPEND_CMD` | `root@beta /usr/local/sbin/beta-suspend` |
| `GAMMA_SUSPEND_CMD` | `manuel@gamma sudo /usr/local/sbin/gamma-suspend` |

### Pitfalls (both verified by troubleshooting on 2026-08-20)

- **The suspend command must use the ssh **alias** (e.g. `beta`), not the raw
  IP.** The `IdentityFile` for the `backup@delta` key lives in
  `/root/.ssh/config` matched on the alias, so `root@10.8.0.5 …` gets
  `Permission denied (publickey)` while `root@beta …` works.
- **The controller unquotes `$suspend_cmd`** so ssh word-splits it into
  `user@host` + the command. It must be an unquoted, untrusted-position-free
  variable; do not re-quote it or ssh treats the whole string as one hostname
  (`hostname contains invalid characters`).

## SSH topology for the controller

Delta reaches the sources as **root** (the systemd service runs as root,
`User=root`), using a dedicated identity `backup@delta` at
`/root/.ssh/id_ed25519_backup`. Verified reachability from Delta:

| From → To | Command | Notes |
|---|---|---|
| Delta → Alpha | `ssh alpha` | **port 2020** (VPS SSH port), user `manuel`, then `sudo` |
| Delta → Beta | `ssh beta` | user `root`, port 22 |
| Delta → Gamma | `ssh gamma` | user `manuel`, port 22 |

Delta's `/etc/hosts` aliases: `alpha`→10.8.0.1, `beta`→10.8.0.5, `gamma`→10.8.0.4.
This is **required** — Delta has no other resolution, and Alpha's SSH is on
2020 not 22.

`/root/.ssh/config` on Delta maps each alias to its `User`, `Port` (alpha=2020),
and `IdentityFile=/root/.ssh/id_ed25519_backup` with `IdentitiesOnly yes`.

The `backup@delta` public key is authorized on each source in **that source's**
account used by the controller:

- Alpha → `manuel`'s `authorized_keys`
- Beta → `root`'s `authorized_keys`
- Gamma → `manuel`'s `authorized_keys`

## Scoped NOPASSWD sudoers (keep these — they are the backup identity, not admin access)

Each source grants the backup identity **only** the commands the controller
needs, via `visudo` files under `/etc/sudoers.d/`:

| Source | File | Grants |
|---|---|---|
| Alpha | `zero-five-backup` | `manuel NOPASSWD: /usr/local/sbin/zero-five-alpha-export, /usr/bin/rsync` |
| Beta | `zero-five-backup` | `root NOPASSWD: /usr/bin/rsync, /usr/local/sbin/beta-suspend` |
| Gamma | `zero-five-backup` | `manuel NOPASSWD: /usr/bin/rsync, /usr/local/sbin/gamma-suspend` |

These are **not** blanket admin grants. Any interactive/human sudo (e.g.
`manuel` on Delta, Alpha, or Gamma) still requires a password. Removing these
files silently breaks the daily job.

## Controller flow (`/usr/local/sbin/zero-five-backup`)

Runs each source in sequence: `delta` (local restic of listed paths), `alpha`
(SSH → run exporter → rsync export dir → restic), `beta`, `gamma` (`backup_host_paths`
rsyncs the manifest paths into a temp dir → restic). Beta/Gamma are wrapped in
the wake/suspend logic above.

Preflight guards refuse to run when: `/srv/nas` is not mounted, the restic
password file is missing/empty, the backup disk is below `MIN_FREE_KIB`, a
required tool (`restic/ssh/rsync/mountpoint/flock/python3`) is absent, a source
manifest is missing, or another run holds `/run/lock/zero-five-backup.lock`.

A source failure stops the all-sources run and leaves existing snapshots
untouched.

## Alpha exporter (`/usr/local/sbin/zero-five-alpha-export`)

Produces an application-consistent export at `/var/lib/zero-five-backup/alpha`:

- PostgreSQL `pg_dump` custom-format dump (not a blind volume copy);
- every MinIO bucket via `mc mirror` (API export, not a live-volume copy);
- the `bot-data` named volume as a gzip tar;
- the exact deployed git commit + `git status --short`;
- `compose.yaml` + the production `.env` (mode 600);
- the application checkout minus reproducible deps/build output.

### Two fixes shipped 2026-08-20 (committed to infra `c802890`, `75aacc0`)

1. **`mc mirror backup/ /export`, not `backup:/ /export`.** The newer
   `minio/mc:latest` client rejects `backup:/` with `Requested path /backup:/
   not found`; `backup/` works. The handbook's earlier "pin the mc image tag"
   warning remains relevant — the exporter's example uses `minio/mc:latest`,
   which is fine for now but could be pinned to a tested client tag.
2. **Idempotent staging:** `rm -rf "$output"` before `mv staging output`. Without
   it, pre-creating `/var/lib/zero-five-backup/alpha` (per the runbook) makes the
   final `mv` fail with `Directory not empty` on reruns. The output dir is a
   throwaway transfer area, so clearing it is safe.

## Adding new applications (e.g. a crypto ledger on Alpha)

**No — the backup does not auto-discover new apps.** It only backs up what is
explicitly listed. Each source is scoped as follows:

| Source | What is backed up | Driver |
|---|---|---|
| Alpha | **only Second Brain** | `/etc/zero-five-backup/second-brain.env` (tells the exporter which containers/volumes/paths to stage) |
| Delta | only the paths in `delta-paths` | `/etc/zero-five-backup/delta-paths` |
| Beta | only the paths in `beta-paths` | `/etc/zero-five-backup/beta-paths` |
| Gamma | only the paths in `gamma-paths` | `/etc/zero-five-backup/gamma-paths` |

A new app on any machine is **invisible** to the controller until its data is
added to the relevant manifest — otherwise it is silently skipped.

### To back up a new app

**Filesystem-only app** (e.g. plain config/data directories): add its paths to
the source's `*-paths` file. The controller rsyncs the listed directories as-is.

**Containerized app with a database + object storage** (the Second Brain
pattern — the correct choice for a crypto ledger): extend **the Alpha
exporter** (`zero-five-alpha-export.sh`) to also stage that app:

1. Add a `pg_dump` for the new app's database (mirror the existing
   `SECOND_BRAIN_DB_*` step) — the SQL dump is the authoritative structured
   export; never copy the live volume.
2. `mc mirror` the new app's buckets, or `docker run … tar` a named volume if
   it has non-DB state.
3. Copy its `compose.yaml` + `.env` + git commit/status into the staging tree.
4. Add the new app's variables to `second-brain.env` (rename to something
   neutral or add a sibling config). Keep secrets out of Git — the populated
   `/etc/zero-five-backup/second-brain.env` is root-readable and mode 600.
5. Reinstall the exporter on Alpha (`sudo install -Dm0755 …`), then
   `sudo /usr/local/sbin/zero-five-backup alpha` to smoke-test.

Because repos use `tag <source>` and each new app just adds to Alpha's staging
tree, **no repo or retention reconfiguration is needed** — only the exporter's
inclusion logic. If you add whole new machines instead of apps, they need a new
entry in the controller's `case` dispatch and a restic repo is auto-created by
`init_repo`.

> The planner step for this lives in the infra repo (`backup/` folder). Design
> before touching machines: add the staging logic, validate with `make
> validate`, then deploy.

## Installation outline

These commands are deployment steps for Delta and the source machines; local
validation does not run them.

On Delta, clone the operational repository:

```bash
sudo install -d -m 0750 /home/manuel/services
git clone git@github.com:Manuel0516/zero-five-infra.git \
  /home/manuel/services/zero-five-infra
sudo install -d -m 0700 /etc/zero-five-backup
sudo cp /home/manuel/services/zero-five-infra/backup/backup.env.example \
  /etc/zero-five-backup/backup.env
sudo cp /home/manuel/services/zero-five-infra/backup/delta-paths.example \
  /etc/zero-five-backup/delta-paths
sudo cp /home/manuel/services/zero-five-infra/backup/beta-paths.example \
  /etc/zero-five-backup/beta-paths
sudo cp /home/manuel/services/zero-five-infra/backup/gamma-paths.example \
  /etc/zero-five-backup/gamma-paths
sudo chmod 600 /etc/zero-five-backup/backup.env
```

Create the repository password interactively in
`/etc/zero-five-backup/restic-password`. Do not place it in Git or a command
line. Install restic, rsync, and the SSH client before enabling the service.

On Alpha, install `scripts/zero-five-alpha-export.sh` as
`/usr/local/sbin/zero-five-alpha-export`, create the root-readable
`/etc/zero-five-backup/second-brain.env` from its example, and configure the
dedicated backup SSH identity to run the exporter and required transfer
operations.

Install the service and timer on Delta:

```bash
sudo install -Dm0755 \
  /home/manuel/services/zero-five-infra/scripts/zero-five-backup.sh \
  /usr/local/sbin/zero-five-backup
sudo install -Dm0644 \
  /home/manuel/services/zero-five-infra/systemd/zero-five-backup.service.example \
  /etc/systemd/system/zero-five-backup.service
sudo install -Dm0644 \
  /home/manuel/services/zero-five-infra/systemd/zero-five-backup.timer.example \
  /etc/systemd/system/zero-five-backup.timer
sudo systemctl daemon-reload
sudo systemctl enable zero-five-backup.timer
```

Run each source manually before enabling the 21:00 timer:

```bash
sudo /usr/local/sbin/zero-five-backup delta
sudo /usr/local/sbin/zero-five-backup alpha
sudo /usr/local/sbin/zero-five-backup beta
sudo /usr/local/sbin/zero-five-backup gamma
```

The current implementation intentionally does not restore data. Verification
checks that snapshots exist, expected exports are present, repositories pass
`restic check`, excluded content is absent, permissions are correct, and the
disk has sufficient capacity.

## Failure and rollback

The job refuses to run when `/srv/nas` is not mounted, the repository password
is missing, the disk is below its free-space threshold, or a source manifest is
missing. A source failure stops the all-sources run and leaves existing
snapshots untouched.

To disable automation while preserving the repositories:

```bash
sudo systemctl disable --now zero-five-backup.timer
```

Removing the service, timer, and scripts does not delete `/srv/nas/backups/`.

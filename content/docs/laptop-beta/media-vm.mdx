Mullvad's egress tunnel. Administration enters through the LAN path from Beta,
with the established Hermes → Delta → Beta → guest SSH chain.

## Current network containment

UFW is active with these effective rules:

```text
Default incoming: deny
Default outgoing: allow
22/tcp inbound:   allow only from 192.168.1.166 (Beta)
22/tcp outbound:  deny for IPv4 and IPv6
```

Mullvad is configured as follows:

```text
Mullvad:          connected
Autoconnect:      on
Lockdown mode:    on
LAN sharing:      allow
```

LAN sharing is intentionally allowed because it preserves the administration path
through Beta. It does **not** override UFW's outbound SSH denial. The VM can still
reach other LAN services over non-SSH protocols; full outbound isolation is a
separate quarantine mode and is not yet implemented.

Inspect the live state:

```bash
mullvad status
mullvad lockdown-mode get
mullvad auto-connect get
mullvad lan get
sudo /usr/sbin/ufw status verbose
ip -brief address
ip route
ss -lntup
```

## Normal operating mode

Normal mode is intended for future downloader setup:

- Mullvad must be connected before download services start.
- Mullvad lockdown stays enabled so a VPN failure fails closed.
- qBittorrent and related services must be bound to the Mullvad path, not the LAN
  interface, when they are installed.
- The guest must not receive a Zero Five mesh address.
- The guest must not mount Gamma's library or the NAS.
- Outbound SSH remains denied even when the VPN is active.

Do not create an automatic VPN-to-direct-internet fallback. A silent fallback would
expose download traffic if the Mullvad account expires or the tunnel fails.

## qBittorrent MVP

The first downloader component is installed as a native Debian service rather than a
Docker media stack. This keeps the first network-boundary test small and observable.

```text
Service:       media-qbittorrent.service
Binary:        /usr/bin/qbittorrent-nox
User:          zero
Profile:       /home/zero/services/media-pipeline/config/qbittorrent
WebUI:         192.168.1.105:8080
Torrent bind:  wg0-mullvad
WebUI auth:    qBittorrent-generated temporary password until changed by operator
```

The service is enabled and starts only when `/sys/class/net/wg0-mullvad` exists. Its
systemd unit uses `NoNewPrivileges`, a private temporary directory, a read-only system
filesystem, and narrowly scoped write paths. The WebUI is allowed through UFW only
from Beta's administrative source `192.168.1.166`.

The qBittorrent directories are:

```text
/home/zero/services/media-pipeline/
├── config/qbittorrent/
├── downloads/incomplete/
├── downloads/complete/
├── quarantine/
├── rejected/
├── manifests/
└── outbox/
```

Retrieve the current temporary WebUI password locally; never store it in this
handbook or send it through chat:

```bash
sudo journalctl -u media-qbittorrent.service --no-pager \
  | grep 'temporary password' \
  | tail -1
```

Log in as `admin`, set a permanent strong password in the WebUI, and do not reuse an
SSH or Mullvad credential. The temporary password changes when the service starts
until a permanent WebUI password is configured.

Verify the service and binding:

```bash
systemctl is-active media-qbittorrent.service
ss -lntup | grep -E '(:8080|:6881)'
grep -E '^(WebUI|Connection|Downloads)' \
  /home/zero/services/media-pipeline/config/qbittorrent/qBittorrent/config/qBittorrent.conf
```

The expected WebUI listener is `192.168.1.105:8080`, not `*:8080`. The qBittorrent
configuration must contain both `Connection\Interface=wg0-mullvad` and
`Connection\InterfaceName=wg0-mullvad`.

The Mullvad-disconnect test is still outstanding. Do not add real media torrents
until this test confirms that qBittorrent stops or cannot make torrent connections
when Mullvad is disconnected. Use a freely redistributable Debian test torrent for
that verification.

## Tor Browser

Tor Browser 15.0.20 is installed at:

```text
/home/zero/Applications/tor-browser
```

Launch it with:

```bash
/home/zero/Applications/tor-browser/start-tor-browser.desktop
```

The archive was downloaded from the official Tor Project distribution host. Its
signature was verified against the Tor Browser Developers primary fingerprint:

```text
EF6E 286D DA85 EA2A 4BA7 DE68 4E2C 6E87 9329 8290
```

The GPG message saying the key was “not certified with a trusted signature” was a
local trust warning, not a bad signature. The key was then imported through the Tor
Project WKD, independently fingerprint-checked, and marked locally trusted. The
final verification reported `Good signature` and `[ultimate]`.

Tor Browser is for web browsing and research only. Do not route qBittorrent or bulk
media traffic through Tor. Tor is not a suitable torrent transport: it is slow,
primarily TCP-oriented, cannot provide a complete all-protocol transparent route,
and torrent clients can leak outside a SOCKS configuration. Bulk downloads remain
Mullvad-bound; an all-internet Tor transparent proxy is intentionally not enabled.

If Mullvad is unavailable, keep the media services stopped. Do not silently fall back
to Tor or direct internet access.

If Mullvad is cancelled or deliberately replaced, the operator must explicitly
switch to direct mode. This is a privacy downgrade, not the default recovery path:

```bash
mullvad disconnect
mullvad lockdown-mode set off
mullvad auto-connect set off
sudo /usr/sbin/ufw default allow outgoing
sudo /usr/sbin/ufw reload
```

The UFW rule denying outbound TCP/22 should remain in place. Verify the public IP
before starting any media downloader:

```bash
curl -4 https://api.ipify.org; printf '\n'
```

Direct mode should be treated as temporary. A replacement WireGuard provider can
use the same fail-closed model; do not merely remove Mullvad and assume the old
kill-switch policy will adapt automatically.

## Quarantine / offline procedure

A future `media-net quarantine` helper should implement this policy atomically:

1. Pause qBittorrent and stop download-related services.
2. Disconnect Mullvad.
3. Keep SSH from Beta available for administration.
4. Deny all outbound traffic, not only TCP/22.
5. Scan only files in a dedicated quarantine directory.
6. Do not mount Gamma, the NAS, or the clean media library.

This is an operational air gap, not a separate kernel trust boundary. For a
particularly suspicious file, use Proxmox to disconnect the guest's virtual NIC and
inspect it through the Proxmox console. A VM-side script cannot guarantee protection
from a guest kernel compromise.

The planned stronger design is a sibling `quarantine-vm` on Beta with no NIC,
ClamAV/YARA/`ffprobe`, signed manifests, and destroy/rebuild on detection. That
architecture is documented separately and is not yet deployed.

## Recovery paths

### SSH recovery

Normal administration uses the existing Beta jump path. Direct guest LAN SSH is
available only from Beta because of UFW:

```bash
ssh zero@192.168.1.105
```

If the guest is unreachable, use the Proxmox console on Beta. The guest TTY remains
the recovery path even when LightDM or the desktop fails. Switch to a TTY with
`Ctrl` + `Alt` + `F3` and log in as `zero`.

### Restore a missing temporary network lease

These commands are a recovery aid, not the durable configuration:

```bash
sudo ip link set ens18 up
sudo ip addr add 192.168.1.105/24 dev ens18
sudo ip route add default via 192.168.1.1 dev ens18
printf 'nameserver 192.168.1.1\n' | sudo tee /etc/resolv.conf
```

The durable source is `/etc/network/interfaces`:

```text
auto ens18
allow-hotplug ens18
iface ens18 inet dhcp
```

Restore the DHCP client and networking if they are missing:

```bash
sudo apt-get update
sudo apt-get install isc-dhcp-client ifupdown
sudo systemctl enable --now networking
```

Do not run a broad `apt autoremove --purge` on this guest. Preserve the active
network stack, SSH, QEMU guest agent, Mullvad, UFW, and LightDM explicitly.

### Restore the graphical login

The current intended display configuration is:

```text
Display manager: lightdm
Greeter:        lightdm-gtk-greeter
Session:        xfce
```

Check it from the TTY:

```bash
systemctl is-active lightdm
systemctl status lightdm --no-pager
journalctl -u lightdm -b --no-pager -n 80
```

If the greeter was removed:

```bash
sudo apt-get install lightdm lightdm-gtk-greeter xfce4 xfce4-terminal
sudo systemctl enable --now lightdm
sudo systemctl set-default graphical.target
```

Keep the Proxmox console open while changing display or network packages.

## RAM and resource explanation

The guest has approximately 4 GiB assigned. Before simplification, Linux reported
about 1.4 GiB used while Cinnamon was running. The largest observed processes were:

- Cinnamon and its session components;
- Xorg;
- several `mullvad-gui` processes;
- GNOME Software;
- Evolution background services;
- Blueman and Nemo desktop helpers.

After replacing Cinnamon with minimal XFCE and retaining only the Mullvad daemon,
Linux reported approximately 615 MiB used, 2.9 GiB free, and 3.2 GiB available.
The current largest desktop processes are Xorg, XFCE panel/window manager/desktop,
LightDM session components, and `mullvad-daemon`.

`free` includes kernel buffers and filesystem cache, so the process percentages do
not add exactly to the `used` value. The meaningful comparison is the available
memory after login: roughly 3.2 GiB is currently available before media services
are installed.

The expected future memory budget is different:

- qBittorrent and a small download stack should fit comfortably;
- Radarr/Sonarr/Prowlarr, Docker, antivirus, and media probing add overhead;
- a quarantine scanner should be run with bounded concurrency;
- do not run a second full desktop, model, or unrelated service in this guest;
- monitor `free -h`, `swapon --show`, and `systemd-cgtop` after each component.

The desktop was therefore a large part of the original RAM increase; qBittorrent now
uses approximately 29 MiB in the verified idle state, and the media pipeline itself
has not yet been exercised with a real torrent.

## Bring-up incident: broad desktop cleanup

The first simplification attempt installed XFCE and then used a broad autoremove.
It removed the guest's DHCP client and NetworkManager assumptions, left the network
interface without an IPv4 lease after reboot, and broke the original graphical
login. The guest was recovered through the Proxmox TTY by bringing `ens18` up and
adding a temporary address/route. A repair pass then installed `isc-dhcp-client`,
configured durable DHCP with `ifupdown`, installed `lightdm-gtk-greeter`, and set
XFCE as the LightDM session.

The lesson is operationally important: a successful APT transaction is not proof
that a guest remains reachable. Any future cleanup must:

1. take a Proxmox snapshot when practical;
2. preserve the actual networking implementation, not a guessed package name;
3. install the replacement display stack first;
4. keep a console open;
5. reboot-test DHCP, SSH, Mullvad, UFW, and LightDM independently;
6. never use broad autoremove until the simulated removal list is reviewed.

## Bring-up incident: qBittorrent profile permissions and INI syntax

The first qBittorrent service attempt crashed because its profile tree was created as
`root:root` while the systemd service runs as `zero`. The service was corrected by
creating the cache directory and recursively assigning the profile to `zero:zero`.

A second attempt wrote qBittorrent INI keys with doubled backslashes. qBittorrent
ignored those entries, resulting in a listener on `*:8080` and no effective interface
binding. The config was rewritten with single backslashes, the service was stopped
before rewriting, and the final verification showed:

```text
Service:   active
WebUI:     192.168.1.105:8080
Mullvad:   connected
Torrent:   wg0-mullvad
HTTP:      200
```

Do not treat a running qBittorrent process as proof of containment. Always inspect the
listener address, the effective config keys, and the Mullvad state before adding a
torrent.

## Future build boundary

The current guest is only the hardened base. The next media work should add one
component at a time, with a RAM/disk/network check after each addition. The target
architecture remains:

```text
media-vm (dirty download side)
  → host-owned transfer boundary on Beta
  → offline quarantine VM
  → signed pull/import into Gamma
```

Until the quarantine VM and signed importer exist, do not treat media files in this
single guest as trusted merely because a scanner reports clean.

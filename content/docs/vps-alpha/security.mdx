The VPS is exposed to the internet 24/7, so security is layered: hardened SSH, a firewall, fail2ban, and unattended security updates. This page documents each layer and how to recreate it.

> **Current audit:** The live review on 2026-07-21 found no confirmed
> compromise, but it did find critical recovery and high-impact least-privilege
> gaps. Read the [dated security audit](/docs/vps-alpha/security-audit-2026-07-21)
> before treating this baseline as sufficient.

## SSH

`sshd` listens on the non-default port **2020** with password logins disabled. Effective settings (from `/etc/ssh/sshd_config` and `/etc/ssh/sshd_config.d/`):

| Setting | Value | Why |
|---------|-------|-----|
| `Port` | `2020` | Cuts automated scan noise on port 22 |
| `PermitRootLogin` | `no` | Root can never log in directly |
| `PasswordAuthentication` | `no` | Password exchange is disabled in `00-zero-five-authentication.conf` |
| `KbdInteractiveAuthentication` | `no` | PAM-backed interactive challenges cannot become a password fallback |
| `AuthenticationMethods` | `publickey` | A valid authorized key is explicitly required |
| `PubkeyAuthentication` | `yes` | Seven ed25519 public keys are installed in `~/.ssh/authorized_keys` (2026-08-14: orphaned `macbook` key removed; keys: `archcraft`, `manuellore05@gmail.com`, three GitHub Actions CI keys, `manuel@delta`, one key without a comment) |

> **Precedence trap found on 2026-07-21:** The root-only
> `50-cloud-init.conf` enabled passwords and sorted before
> `60-cloudimg-settings.conf`, which disabled them. OpenSSH generally keeps the
> first value it reads for these global options, so the later `no` did not win.
> The declared files looked safe while `sshd -T` and a real connection both
> reported `publickey,password`. The `00-` override now sorts first. Always
> inspect effective state; never infer it from one file.

The MacBook connects via the `contabo` alias — see the [MacBook SSH page](/docs/macbook/ssh) for the client side.

### Harden a fresh server

```bash
# 1. Copy your key first (while password auth still works)
ssh-copy-id -p 22 manuel@NEW_IP

# 2. Keep the current session open and back up the SSH configuration
sudo cp -a /etc/ssh /root/ssh-backup-before-hardening

# 3. Set Port 2020 in /etc/ssh/sshd_config, then create the earliest drop-in
sudoedit /etc/ssh/sshd_config.d/00-zero-five-authentication.conf
```

The drop-in contains:

```text
PasswordAuthentication no
KbdInteractiveAuthentication no
AuthenticationMethods publickey
PubkeyAuthentication yes
PermitRootLogin no
```

Validate and apply only after the public key works:

```bash
# 4. Allow the new port in UFW BEFORE touching the daemon
sudo ufw allow 2020/tcp

# 5. Validate syntax and effective authentication, then reload
sudo sshd -t
sudo sshd -T -C user=manuel,host="$(hostname)",addr=127.0.0.1 \
  | grep -E '^(port|permitrootlogin|passwordauthentication|kbdinteractiveauthentication|authenticationmethods|pubkeyauthentication) '
sudo systemctl reload ssh
```

> **Warning:** Keep the working session open and test `ssh -p 2020 manuel@IP`
> from a second terminal before logging out. A syntax check cannot prove that
> the correct public key is available from the client.

## Firewall (UFW)

> **History:** until 2026-07-11 the box ran **without an active firewall** — `ufw.service` was enabled in systemd, but the firewall itself reported `Status: inactive`. `systemctl` status says nothing here; **`sudo ufw status` is the only source of truth**. Beware a second trap: while UFW is inactive, `ufw status` hides the rules stored in `/etc/ufw/user.rules` — activation resurrected years-old allows (public `3000/tcp`, `2222/tcp`, port 22) that then had to be deleted. Activation and cleanup produced the rule set below.

| Rule | Purpose |
|------|---------|
| `2020/tcp` | SSH |
| `80/tcp`, `443/tcp` | Traefik (HTTP redirect + HTTPS) |
| `25565/tcp` | Minecraft |
| `51820/udp` | WireGuard handshake |
| `from 172.16.0.0/12 to any port 3000 proto tcp` | Traefik (container) → Open WebUI on the host — while public `:3000` stays closed |
| `from 172.16.0.0/12 to any port 8765 proto tcp` | hub-backend (container) → hub-agent on the host |
| `from 172.16.0.0/12 to any port 9119 proto tcp` | Traefik (container) → Hermes dashboard on the host (see [Hermes Agent](/docs/vps-alpha/hermes-agent)) |
| `allow in on wg0` | VPN traffic is trusted (laptop → Ollama `10.40.0.1:11434`) |

Everything else is denied by default: Open WebUI is **VPN-only** via `https://ai.zero-five.space` (Traefik `ipWhiteList 10.40.0.0/24` + DNS → `10.40.0.1`, see [The VPN-only pattern](/docs/vps-alpha/handbook#the-vpn-only-pattern)), and hub-agent (`:8765`) and Minecraft RCON (`:25575`) — which listen on all interfaces — are no longer exposed. Services bound to `127.0.0.1` (ollama-router `:11435`, SearXNG `:8081`) were never reachable regardless.

### Docker and UFW — two traps

1. Ports **published by Docker** (`ports:` in a compose file, like Traefik's 80/443) bypass UFW completely — Docker's NAT rules run first. Never rely on UFW to protect a published port; bind it to `127.0.0.1` instead, as SearXNG does.
2. Traffic from containers **to host services** (host-networked or via `host.docker.internal`) *does* hit UFW's input chain. That is why the Docker address space `172.16.0.0/12` gets scoped allows for `3000` and `8765` — enabling UFW without them takes down `ai.zero-five.space` and the hub's Minecraft controls.

### Recreate

Order matters: define every rule first (nothing applies until `enable`), and keep a working SSH session open.

```bash
sudo ufw default deny incoming && sudo ufw default allow outgoing
sudo ufw allow 2020/tcp                # SSH — never enable without this
sudo ufw allow 80/tcp && sudo ufw allow 443/tcp
sudo ufw allow 25565/tcp && sudo ufw allow 51820/udp
sudo ufw allow from 172.16.0.0/12 to any port 3000 proto tcp
sudo ufw allow from 172.16.0.0/12 to any port 8765 proto tcp
sudo ufw allow from 172.16.0.0/12 to any port 9119 proto tcp
sudo ufw allow in on wg0
sudo ufw --force enable
```

Then verify from another machine that SSH and Minecraft still work, that `http://95.111.229.142:3000` times out, and that `https://ai.zero-five.space` and `https://hub.zero-five.space` load **from inside the VPN** while answering 403 from the public internet.

## fail2ban

Fail2ban watches authentication logs, counts repeated failures from each source
IP, and temporarily bans sources that exceed the jail's threshold. A **jail**
combines a log filter with a firewall action. It supplements public-key-only SSH;
it does not prevent provider-console access, detect every intrusion, or protect
a stolen valid key by itself.

### Observed configuration — 2026-11-17

The live configuration is `/etc/fail2ban/jail.d/defaults-debian.conf`, not the
historically documented `jail.local`. It enables the SSH jail, the systemd
backend, and nftables actions. **The audit found an enforcement mismatch:** SSH
listens on `2020`, but the Fail2ban rule initially targeted `22`. This was
corrected and live-verified on 2026-11-17. A running daemon and increasing ban
counters alone do not establish that the correct port is protected.

**Deployed and verified:** `/etc/fail2ban/jail.d/99-zero-five-sshd.local`
explicitly sets:

```ini
[sshd]
port = 2020
```

It retains the existing backend, filters, thresholds, and ban durations. Only
the Fail2ban SSH jail is reloaded with restart semantics; `sshd` itself is not
restarted or reconfigured. A temporary ban of documentation-only address
`192.0.2.123` must produce a live nftables rule for TCP `2020`, then be removed.
Do not test by deliberately banning the current administrator's address.

```bash
sudo fail2ban-client -t
sudo fail2ban-client status sshd
sudo fail2ban-client get sshd actions
sudo nft list table inet f2b-table
# Remove a particular ban only after checking its reason:
sudo fail2ban-client set sshd unbanip ADDRESS
```

### Audited maintenance repairs — 2026-11-17

**Status: deployed and verified on 2026-11-17 at approximately 10:15 CET.**
The owner ran the privileged helper; its `complete: true` result was corroborated
by independent live read-back: the nftables rule targets TCP `2020`, its test ban
is absent, Fail2ban is active, `sudo -n -l` no longer emits a syntax error, the
local logrotate diversion is registered, `logrotate.service` reports
`Result=success` and `ExecMainStatus=0`, and SSH still listens on `2020`.
The helper transcript additionally records successful `visudo -c`, Fail2ban
configuration testing, the temporary ban/unban, and `sshd -t`.

Rollback files for this application are in
`/var/backups/zero-five-security/20261117T091503Z/`. No SSH or network restart
was performed. Six regression tests and the handbook type/lint/production-build
checks passed before application; the documentation is validated again after
this status update. Source and documentation remain uncommitted unless separately
authorized.

Operational source:
`zero-five-infra/scripts/repair-alpha-security.py`; regression tests:
`zero-five-infra/tests/test_repair_alpha_security.py`.

The approved repair is limited to:

1. Replacing the unsupported sudoers argument
   `/usr/bin/journalctl --unit=*` with the narrower literal
   `/usr/bin/journalctl --unit=ssh.service`. Other grants are preserved; no
   unrestricted journal or shell permission is added. Validate the candidate
   and the complete policy using `visudo` before continuing.
2. Keeping `/etc/logrotate.d/cloud-init-base` and registering a local
   `dpkg-divert` for the byte-identical duplicate
   `/etc/logrotate.d/cloud-init`, moved outside the include directory to
   `/etc/logrotate.zero-five-disabled/cloud-init`. Both installed cloud-init
   packages ship the same stanza; this caused the duplicate-entry error before
   the provider incident. The diversion keeps package upgrades from silently
   restoring that duplicate. Abort if the stanzas differ; do not discard unique
   rotation settings.
3. Installing and verifying the explicit Fail2ban SSH port override above.

Run on Alpha, entering the sudo password only in the local terminal:

```bash
sudo /usr/bin/python3 /home/manuel/services/zero-five-infra/scripts/repair-alpha-security.py --apply
```

The helper preserves root-only rollback files under
`/var/backups/zero-five-security/` and saves owner-readable verification output
under `/home/manuel/services/security-maintenance/` with directory mode `0700`
and file mode `0600`. It checks `visudo`, Fail2ban configuration, actual ban and
unban behavior, logrotate debug validation, a normal non-forced
`logrotate.service` execution, and the retained SSH listener. Review
`status.json` and `verification.txt`; only `complete: true` plus independent
read-back establishes completion. It does not restart networking or SSH.

If a check fails, the helper attempts to restore its configuration changes and
records any rollback failures. It cannot undo log rotation already performed;
restoring the old sudoers file also restores its known syntax error. For manual
rollback, use the timestamped backups to restore only the changed policy and
Fail2ban override, reload the SSH jail, and reverse the local diversion:

```bash
sudo dpkg-divert --local --rename --remove \
  --divert /etc/logrotate.zero-five-disabled/cloud-init \
  /etc/logrotate.d/cloud-init
```

Reversing that diversion restores the known duplicate rotation error; do it only
as part of a reviewed alternative fix. Keep backups private and do not publish
raw authentication logs.

## Secrets policy

Secrets never enter git. Where they actually live:

| Secret | Location |
|--------|----------|
| Hub tokens, Cloudflare DNS API token, admin password | `~/services/hub/.env` |
| Second-brain DB/MinIO/JWT/Google/OpenRouter secrets | `~/services/second-brain/.env` |
| Telegram bot token | `~/services/telegram-translation-bot/.env` |
| Traefik dashboard basic-auth hash | `~/services/hub/traefik/.htpasswd` |
| Hub-agent bearer secret + Minecraft RCON password | `/etc/hub-agent.env` (root:root, mode 600), loaded by the unit via `EnvironmentFile` |
| WireGuard private keys | `/etc/wireguard/wg0.conf` (root-only) |
| GitHub Actions deploy key | Repo secrets `VPS_HOST` / `VPS_SSH_KEY` on GitHub |

Every repo ships a committed `.env.example` documenting the required variable names. When rebuilding, copy it and fill in fresh values:

```bash
cp .env.example .env && vim .env
```

Runtime secret files should be owned by the service operator and mode `600`.
The 2026-07-21 audit corrected several files from `664` to `600`. A filename is
not a security boundary: `personal-ai/server/.env` was also found tracked with
non-secret endpoint values. It must still be replaced by a committed example
and an ignored runtime file before someone later adds a real credential.

> **Warning:** Rotate any secret that may have leaked (e.g. a unit file pasted into a chat or issue). The hub-agent secrets originally lived as `Environment=` lines inside the world-readable unit file; `~/security-fixes.sh` (2026-07-11) moved them into root-only `/etc/hub-agent.env` and rotated the bearer secret. Never put secrets back into `*.service` files — they are mode 644 by default.

> **Accepted risk — 2026-07-21:** Four Hub-stack credentials were emitted by a
> non-quiet Compose audit command. A first atomic rotation attempt rolled back
> after a readiness race, and the owner declined another rotation. The dated
> audit records the impact. File mode `600` protects storage on disk but cannot
> make an already emitted value secret again.

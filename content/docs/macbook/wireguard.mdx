The MacBook joins the [WireGuard mesh](/docs/raspberry/vpn-gateway) as
`10.8.0.11/32` with two peers: the **VPS** (`10.8.0.1`) for Alpha-hosted
services, and **Delta** (`10.8.0.2`) for the home resolver and future
home-hosted apps. The Delta peer uses a public DNS endpoint so it works both
at home and roaming; ordinary internet traffic stays outside the tunnel.

The App Store WireGuard application was installed initially. **As of 2026-08-23 it is the
recommended way to bring the tunnel up** — the Homebrew `wg-quick` CLI does NOT reliably
attach a DNS resolver for private names while roaming (see [Why private names failed on
the MacBook](#why-private-names-failed-on-the-macbook)); the app's Network Extension
attaches DNS to the tunnel itself. The CLI remains installed for `wg show` inspection.

## The Delta roaming endpoint (`delta-vpn.zero-five.space`)

Delta's mesh port (`51821/udp`) is port-forwarded on the home router. The
MacBook's Delta peer points at a **Cloudflare A record** instead of a raw IP:

| Property | Value |
| --- | --- |
| Name | `delta-vpn.zero-five.space` |
| Type / content | A → home WAN IP (46.162.95.145 as of 2026-08) |
| Proxy | **grey cloud (`proxied=false`)** — Cloudflare proxying would terminate WireGuard (it only speaks HTTP); this is a DNS-only record |
| Port | 51821 (Delta's `ListenPort` on `wg0`) |

Because the endpoint is a DNS name, the same config works at home (hairpin NAT
via the router) and roaming (direct to the home WAN IP). WireGuard re-resolves
the endpoint and learns Delta's current address from the handshake; Delta's own
config may show a stale endpoint for the MacBook until the first handshake
updates it — that is expected and harmless.

## Install the CLI

```bash
brew install wireguard-tools
command -v wg
command -v wg-quick
wg --version
brew list --versions wireguard-tools wireguard-go
```

Installing the tools does not create keys, routes, or a tunnel. On macOS,
`wireguard-go` creates a userspace tunnel attached to a dynamic `utunN`
interface. The number may change and must never be hard-coded.

## Routing policy

```text
MacBook                              VPS / Delta
10.8.0.11/32  -------------------->  10.8.0.1/32   (VPS,   95.111.229.142:51820)
             -------------------->  10.8.0.2/32   (Delta, delta-vpn.zero-five.space:51821)

              no WireGuard route for 10.8.0.12+ or internet (default route untouched)
```

`AllowedIPs` covers only `10.8.0.1/32` and `10.8.0.2/32` — macOS installs two
host routes; the default route stays on the normal interface. Other mesh nodes
(MSI `10.8.0.12`, etc.) are not routed through this tunnel, matching the
gateway design where only Beta/Gamma use Delta as egress.

## Files and ownership

| Location | Path | Purpose |
| --- | --- | --- |
| Infrastructure repo | `wireguard/macbook.conf.example` | Secret-free operational source |
| MacBook | `~/.config/wireguard/keys/macbook.key` | Private key, mode `0600` |
| MacBook | `~/.config/wireguard/keys/macbook.pub` | Public key |
| MacBook | `/opt/homebrew/etc/wireguard/zero-five.conf` | Deployed tunnel config, mode `0600` |
| VPS | `/etc/wireguard/wg0.conf` | Persistent hub config, root-owned and mode `0600` |

The example contains the real public routing metadata and a
`MACBOOK_PRIVATE_KEY` placeholder. There is no generator. The private value is
inserted only into the Mac's root-readable deployed copy.

## Create or rebuild the Mac configuration

Generate a keypair only if the Mac does not already have one:

```bash
umask 077
mkdir -p ~/.config/wireguard/keys
wg genkey | tee ~/.config/wireguard/keys/macbook.key \
  | wg pubkey > ~/.config/wireguard/keys/macbook.pub
chmod 600 ~/.config/wireguard/keys/macbook.key \
  ~/.config/wireguard/keys/macbook.pub
```

Never regenerate an active keypair casually: doing so changes the public
identity expected by the VPS.

Validate and copy the source:

```bash
cd /Users/manuel/Desktop/zero-five/zero-five-infra
make validate
sudo install -m 600 wireguard/macbook.conf.example \
  /opt/homebrew/etc/wireguard/zero-five.conf
sudoedit /opt/homebrew/etc/wireguard/zero-five.conf
```

In `sudoedit`, replace `MACBOOK_PRIVATE_KEY` with the existing private key.
Review the file without pasting it into chat or logs. Confirm permissions:

```bash
sudo stat -f '%Sp %Su:%Sg %N' \
  /opt/homebrew/etc/wireguard/zero-five.conf
```

Expected mode is `-rw-------`. A failed edit can be rolled back by stopping the
tunnel and restoring the previous root-owned copy.

## Add the Mac peer safely

This procedure is already complete for the current Mac identity. Use it only
for recovery or an intentional identity replacement.

1. Run `make validate` locally.
2. Keep the existing VPS SSH session open and establish a second session.
3. On the VPS, back up `/etc/wireguard/wg0.conf` with root ownership and mode
   `0600`.
4. Add the Mac public key to the running interface first:

```bash
sudo wg set wg0 peer MACBOOK_PUBLIC_KEY allowed-ips 10.8.0.11/32
```

5. Start the Mac tunnel and validate both machines.
6. Only after runtime validation, add the same public peer block to the VPS
   persistent config. Do not overwrite its private key or laptop peer.

The runtime-first sequence protects the existing tunnel. `wg set` changes the
kernel's live WireGuard device without restarting `wg0`; a bad new peer can be
removed without disrupting the established laptop peer.

## Start and validate

```bash
sudo wg-quick up zero-five
sudo wg show
route -n get 10.8.0.1
route -n get 10.8.0.2
route -n get default
scutil --dns | grep -A2 "resolver #1" | head -5   # confirm DNS = 10.8.0.2, 1.1.1.1 applied
ping -c 3 10.8.0.1
ping -c 3 10.8.0.2
# AdGuard UI via Delta (mesh):
curl --fail --show-error --max-time 5 http://10.8.0.2:80/ -o /dev/null -w '%{http_code}\n'
```

Expected results:

- `10.8.0.1` and `10.8.0.2` use the dynamic `utunN` interface;
- `10.8.0.2` handshakes with Delta through the home router (hairpin NAT at
  home) or the public WAN IP (roaming) — `sudo wg show` reports a recent
  handshake for both peers;
- `scutil --dns` shows the tunnel resolver with `10.8.0.2` + `1.1.1.1`
  (AdGuard first, Cloudflare fallback);
- the default route remains on the normal network interface;
- the VPS responds to ping and the private Ollama API; Delta responds to
  ping and `http://10.8.0.2:80/` returns 302 (AdGuard login redirect).

On Delta, also confirm the mesh peer, nftables, and `wg0` remain in their
previous state. A handshake alone does not prove route or application policy.

## Why private names failed on the MacBook (roaming) — and the WireGuard-app fix

**Diagnosed 2026-08-23.** Symptom: `router.zero-five.space` (and other private names)
said **"Server Not Found"** on the MacBook while **roaming**, yet worked from the iPhone
(the same tunnel resolver) and worked on the Mac when on the home LAN. The phone worked,
the Mac did not — with the *same* name through the *same* tunnel. That asymmetry is the
trap: it points the finger at the machine, not the network.

Root cause is a **macOS-specific wg-quick DNS leak**, not routing or a broken service.
The Homebrew `wg-quick` CLI applies the tunnel's `DNS = 10.8.0.2` line by writing that
address onto macOS's **Wi-Fi (en0) resolver — not onto the tunnel's `utunN` interface.**
So `10.8.0.2:53` (AdGuard) is allowed through the tunnel (the tunnel is a path, not a DNS-server bearer), but the resolver macOS is actually asking lives on en0 and its
queries travel **out the Wi-Fi carrier**, never entering the tunnel:

Verified:
- A DNS query sent **from the tunnel IP `10.8.0.11`** → works (AdGuard answers).
- The **same query from the Wi-Fi IP `192.168.1.109`** → times out.
- `curl` uses macOS's resolver on Wi-Fi, so it fails — even though `curl -k https://10.8.0.2/` with a `Host:` header reached the router directly (that used the routed IP directly, not DNS).

So the name was never failing to *route* — it was failing to *resolve*, because the
resolver sits on the wrong interface. `curl` to the raw IP `http://10.8.0.2:8006`-style
worked; `curl https://router.zero-five.space`-style ("server not found") failed.

**Do NOT "fix" this by adding a public Cloudflare A record for `router.zero-five.space`**
to make the name resolve globally. That publishes a private Zone-2 home-app name into
public DNS — exactly the user probe that was already made for `router` earlier and
rejected (`dns.zero-five.space`, `proxmox`, `jellyfin`, and similar private names must
remain **AdGuard-rewrite-only**; this is the hard rule in the skill). The `router`
Cloudflare A record was already added once and removed; never re-add it.

**The right fix — attach DNS to the tunnel, not to Wi-Fi:**

Option A (recommended, chosen 2026-08-23): use the **WireGuard macOS app** (App Store,
Network Extension). The app assigns the tunnel `DNS =` to the tunnel's virtual interface
scoped resolver, so queries are encapsulated and reach AdGuard. Import `zero-five.conf`
by exporting it with the app or sharing the config; the CLI config remains the source
of truth for keys/routes.

Option B (home-LAN footnote — NOT roaming): while physically at home only, you can instead
just set the Wi-Fi DNS to Delta's LAN address (`192.168.1.106`) so macOS queries AdGuard
directly on the LAN without needing the tunnel at all:
`sudo networksetup -setdnsservers Wi-Fi 192.168.1.106 1.1.1.1`. This is **home-only**
and no longer works roaming; the WireGuard app (Option A) is the long-term fix and is
the chosen path.

**The working recovery when the tunnel breaks on the MacBook (verified 2026-08-23):**

When you toggle the tunnel off/on (or macOS clobbers the resolver after wg-quick), private
names stop resolving and stay broken across retries. **Before bringing the tunnel back up**,
reset the Wi-Fi resolver to default (Empty) and flush the caches:

```bash
sudo networksetup -setdnsservers Wi-Fi Empty
sudo dscacheutil -flushcache
sudo killall -HUP mDNSResponder
```

Then start the tunnel. This clears the stale resolver that wg-quick left attached to en0 so
the fresh tunnel attach takes cleanly. If you're using the CLI, this is the reliable reset
before every tunnel up — the WireGuard app (Option A) avoids needing it.

**Verify after switching:** `curl https://<name>.zero-five.space` must resolve; if it
still says server-not-found, `scutil --dns` shows whether `10.8.0.2` ended up on a
tunnel-scoped resolver or got dropped to en0.

| Symptom | Check |
| --- | --- |
| `wg-quick` rejects the config | Private-key placeholder was not replaced, syntax, or permissions |
| No handshake with VPS | VPS endpoint, UDP firewall, public-key match, internet access |
| No handshake with Delta | `delta-vpn.zero-five.space` resolves to the current home WAN IP; record must be **grey cloud** (proxied=false); router port-forward UDP 51821 → 192.168.1.106; Delta's public key matches |
| Handshake but no VPS access | `AllowedIPs`, macOS route, VPS UFW, service binding |
| Handshake but no Delta access | `AllowedIPs` must include `10.8.0.2/32`; Delta's `sport 51821 lookup main` rule (else the Mullvad tunnel swallows replies) |
| Internet unexpectedly uses VPN | `AllowedIPs` is broader than `10.8.0.1/32` + `10.8.0.2/32` |
| Works manually but not after reboot | No verified startup service yet |
| Private names "Server Not Found" only while roaming (works on phone/LAN) | Homebrew wg-quick attaches `DNS=` to Wi-Fi (en0), not the tunnel → queries leak out the carrier and never reach `10.8.0.2`. Use the WireGuard macOS app (Network Extension) instead; do NOT add a public Cloudflare A record for the private name |

## Rollback

Stop the Mac tunnel:

```bash
sudo wg-quick down zero-five
```

If this was a new or replacement peer, remove only that live peer on the VPS:

```bash
sudo wg set wg0 peer MACBOOK_PUBLIC_KEY remove
```

If persistent configuration changed, restore the protected VPS backup and
restart `wg-quick@wg0` from the still-open SSH session. Recheck the laptop peer
and private Ollama path. Do not change UFW or SSH during this rollback.

To remove only the Mac CLI after the tunnel is down:

```bash
brew uninstall wireguard-tools
```

Review `brew autoremove` separately before allowing it to remove dependencies.

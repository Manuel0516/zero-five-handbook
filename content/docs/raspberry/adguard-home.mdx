> **Status: DEPLOYED 2026-08-22.** AdGuard Home runs in Docker on Delta,
> resolving private `zero-five.space` names over the LAN + WireGuard mesh,
> with ad-blocking and encrypted DoH/DoT upstreams. Roadmap item "Private DNS
> and remote access" — see [Infrastructure Roadmap](/docs/roadmap).

Delta gets a private, VPN-aware DNS resolver so home hosts and future
home-hosted apps resolve by stable names over the LAN + WireGuard mesh.
AdGuard Home runs in Docker on Delta. It binds **only** to the LAN and
WireGuard interfaces — it never answers on a public network — and forwards
resolvable names on, so it is a forwarder, not an open recursive resolver.

This is deliberately **independent of Alpha**. It is the home resolver,
managed by Delta, used by every LAN/VPN client. Public Cloudflare DNS for
`zero-five.space`, and Traefik on Alpha, are untouched.

## Why

The fleet currently reaches services by remembered IPs and scattered per-device
`/etc/hosts`. As apps migrate off Alpha (personal-ai, minecraft, monitoring),
their names must stay stable even as their host changes. A single private
resolver gives:

- stable **host** names for every mesh peer (`alpha`, `delta`, `gamma`,
  `beta`, `macbook`, `msi`, `blackarch`) with `.zero-five.space`;
- stable **app** names that follow the service wherever it is deployed;
- **ad-blocking + per-client filtering** (the same motivation as the Pi-hole
  option, with a lighter footprint on Delta);
- a consistent resolver DNS that every VPN client already points at, so no
  per-device hosts-file drift.

## Decision log (from design conversation, 2026-08)

- **Tool: AdGuard Home**, not Pi-hole — lighter on Delta (which already runs
  the backup controller and the Mullvad gateway), cleaner per-client
  filtering, and better upstream DoH/DoT support.
- **Names: flat under `zero-five.space`, no `home.` sub-zone.** The user does
  not want a sub-path distinction; almost nothing will be public anyway.
  AdGuard is authoritative for records pinned to the mesh, and forwards
  everything else (including the public/in-use `zero-five.space` records) so
  VPN clients see the same public names as the wider internet.
- **Delivery: Docker Compose** on Delta, matching the other services and
  making it easy to back up and redeploy.
- **Storage: on the Pi's own disk**, `/home/manuel/services/adguard/` — NOT
  under `/srv/nas/` (external drive). User correction 2026-08-22: a resolver
  must work even if the NAS is unplugged. The initial deploy used
  `/srv/nas/apps/adguard/` (from the original proposal) and was moved.

## Zone / name model

Two behaviors in one resolver:

1. **Public names already in Cloudflare** (`hub`, `brain`, `ai`, `docs`,
   `hermes`, wildcard-covering public services, `mc`) — AdGuard **forwards**
   upstream, so VPN clients resolve the same records the internet does.
2. **Private host/app names** — AdGuard answers from local (rewritten)
   **authoritative** records that are visible **only** on the LAN/VPN and
   never copied to a public authoritative server.

This mirrors the "pick per name" model: only the private names are local; the
rest are proxied so nothing mirrors stale.

| `dns.zero-five.space` | 10.8.0.2 — admin UI (`http://dns.zero-five.space`, port 80 → container 3000) |

App records follow the service — when `personal-ai`, `minecraft`, or the
monitor moves to Gamma/Delta, it keeps a stable flat name that points at
whatever currently hosts it. Adding one is a single AdGuard rewrite
(`Settings → DNS rewrites`, or `POST /control/rewrite/add`).

## Binding / hardening

- Docker publishes **only** on `10.8.0.2:53` (mesh) + `192.168.1.106:53`
  (LAN), TCP and UDP; admin UI on `3000` on both. No public interface.
- Upstream is **encrypted** DoH/DoT: `https://1.1.1.1/dns-query`,
  `https://dns.google/dns-query`, `tls://8.8.8.8` (bootstrap `1.1.1.1`,
  `8.8.8.8`) — a forwarder, not an open recursive resolver, so it cannot be
  used as a DRDoS reflector.
- **AdGuard DNS filter** blocklist enabled (ad-blocking live, verified
  `doubleclick.net` → `0.0.0.0`).

## Deployment (Docker Compose on Delta)

Live compose project at `/home/manuel/services/adguard/compose.yaml`:

```yaml
name: adguard

services:
  adguardhome:
    image: adguard/adguardhome:latest
    container_name: adguardhome
    restart: unless-stopped
    volumes:
      - /home/manuel/services/adguard/work:/opt/adguardhome/work
      - /home/manuel/services/adguard/conf:/opt/adguardhome/conf
    ports:
      - "10.8.0.2:53:53/tcp"
      - "10.8.0.2:53:53/udp"
      - "192.168.1.106:53:53/tcp"
      - "192.168.1.106:53:53/udp"
      - "10.8.0.2:80:3000/tcp"
      - "192.168.1.106:80:3000/tcp"
      - "10.8.0.2:3000:3000/tcp"
      - "192.168.1.106:3000:3000/tcp"
    cap_add:
      - NET_ADMIN
```

(`dns.zero-five.space` rewrite → 10.8.0.2; port 80 is published → container
3000 so `http://dns.zero-five.space` opens the admin UI without a port
suffix. AdGuard only binds LAN/mesh IPs at the host level.)

Docker itself was installed via Debian apt (`docker.io` + `docker-compose`,
both in trixie) — no third-party Docker repo needed on Delta.

## Mesh adoption (in progress)

Each WireGuard client peer gains `DNS = 10.8.0.2` so every VPN-connected
device resolves home names + ad-block automatically.

Status 2026-08-22:

- **MacBook (10.8.0.3)** — on the mesh via `delta-vpn.zero-five.space:51821`
  roaming endpoint (grey-cloud A record → home WAN IP, router forwards UDP
  51821 → Delta); its `AllowedIPs` includes `10.8.0.2/32` so AdGuard is
  reachable. Handshake + AdGuard UI verified 2026-08-22. See
  [MacBook WireGuard](/docs/macbook/wireguard). `DNS = 10.8.0.2` per-peer
  line not yet applied.
- **Beta/Gamma/MSI/phone** — not yet adopted; each client edit needs its own

Rollback is removing the `DNS =` line (or `AllowedIPs` entry) from each peer;
nothing public changes.

## Pitfalls (hit during deployment 2026-08-22)

- **The Mullvad gateway's nftables forward chain blocked container traffic.**
  `/etc/nftables.conf` on Delta has a `gateway` table with
  `policy drop` on the forward chain, originally accepting only Beta/Gamma
  sources. That silently killed *all* forwarded traffic to/from Docker
  containers: mesh/LAN clients → AdGuard DNS timed out (DNAT counters showed
  packets arriving, forward chain dropped them), and AdGuard → upstream DoH
  also died. Fix: accept local subnets + docker bridge interfaces in the
  forward chain:
  ```
  ip saddr 10.8.0.0/24 accept
  ip saddr 192.168.1.0/24 accept
  iifname "br-*" accept
  iifname "docker0" accept
  ```
  Applied live (`nft add rule`) and persisted in `/etc/nftables.conf`
  (backup: `/etc/nftables.conf.bak-adguard`). Any new container service on
  Delta needs this already-covered (local subnets + bridge), but re-verify
  after editing the ruleset.
- **AdGuard v0.107.x first-run API changed.** The old `/control/setup_install`
  endpoint is gone; it is `POST /control/install/configure` with a flat body
  (`username`, `password`, `web: {ip, port}`, `dns: {ip, port}`,
  `language`). The web UI redirects everything to `/install.html` until setup
  completes, which confused early API attempts.
- **Admin credentials cannot be changed from the UI/API in v0.107.79.** The
  Settings page has no password option and `/control/profile/update` only
  handles language/theme. To rotate: stop the container (AdGuard rewrites its
  config on shutdown — edit **after** stop), edit
  `conf/AdGuardHome.yaml` `users:` block with a bcrypt hash (`python3 -c
  "import bcrypt; print(bcrypt.hashpw(b'PW', bcrypt.gensalt(rounds=10,
  prefix=b'2a')).decode())"`), then start again.
- **Filter needed a refresh after the nftables fix**: rules_count was 0 until
  `POST /control/filtering/refresh` (container outbound had been blocked).

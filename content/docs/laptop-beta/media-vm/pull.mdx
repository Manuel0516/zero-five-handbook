## Current status

The Delta-terminated pull path is deployed and verified with a harmless fixture.
The verified route is:

```text
Delta media-pull client
        ↓ client-specific SSH key
Delta media-relay account
        ↓ fixed forced command and root-only wrapper
Delta upstream SSH key
        ↓ read-only rsync
media-vm media-outbox account
        ↓
media-vm outbox/ plus companion manifests
        ↓
Delta staging or an operator-selected destination
        ↓
manifest and SHA-256 verification
```

Verified on 2026-08-26:

- Delta can authenticate to media-vm with the dedicated upstream key.
- The media-vm host key is pinned on Delta.
- The restricted `media-outbox` account can read only the clean outbox path.
- Delta can authenticate to its local terminating relay with a separate client key.
- `media-pull --list` returns only manifest-backed clean items.
- A selected fixture was pulled into Delta staging and verified with SHA-256.
- The source item remains on media-vm after the pull; source deletion is not automatic.

The two `Could not chdir to home directory /nonexistent` messages that may appear during a pull are cosmetic account-home warnings. They do not indicate a transfer or verification failure.

## Trust and source boundary

The source is deliberately fixed to the clean outbox:

```text
/home/zero/services/media-pipeline/outbox/
```

The relay never exposes these paths:

```text
/home/zero/services/media-pipeline/downloads/complete/
/home/zero/services/media-pipeline/downloads/browser-inbox/
/home/zero/services/media-pipeline/quarantine/
/home/zero/services/media-pipeline/rejected/
/home/zero/services/media-pipeline/manifests/scan-reports/
```

A destination cannot choose an arbitrary path on media-vm. It can select only safe relative
paths inside `outbox/` that are present and have a matching `<item>.manifest` companion.
A selected item may be a regular file or a folder. This prevents a client from bypassing
quarantine or reading private scanner reports.

The eligible source files may have originated from qBittorrent, Firefox, or Tor Browser. Origin does not affect trust: all three inputs pass through the same quarantine, ClamAV, YARA, `ffprobe`, SHA-256, verdict, and manifest process.

## Installing the Delta command

The installed command is:

```text
/home/manuel/.local/bin/media-pull
```

The current live copy is owned by `manuel`, mode `0755`, and has been syntax-validated and installed from the infrastructure repository. It is intended to be in Delta's normal user `PATH`; if a new login does not find it, use the absolute path or add this to the user's shell profile:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

The command uses this default identity when `--identity` is omitted:

```text
$HOME/.ssh/zero-five-media-relay
```

The private client key stays on the destination computer. It is not stored in the infrastructure repository or copied to media-vm.

## List available files

On Delta, list only clean items that have manifests:

```bash
media-pull \
  --delta 10.8.0.2 \
  --identity /home/manuel/.ssh/zero-five-media-relay \
  --list
```

The list is generated by a metadata-only rsync listing of the media-vm outbox. It does not
transfer media contents, so it remains responsive even when the outbox contains large
files. Selected pulls print a transfer header with the destination and selected item names before
opening the relay stream. The relay's rsync progress is emitted on SSH stderr and remains
visible while the archive is being prepared. It includes per-file progress plus transferred
bytes, overall percentage, transfer rate, and ETA. Progress never enters the tar data stream.
The final `MEDIA_PULL_VERIFIED` line is the success boundary.

The current harmless verified fixture is:

```text
relay-manifest-test.txt
```

## Pull one selected file

Choose a destination directory on the computer running `media-pull`:

```bash
media-pull \
  --delta 10.8.0.2 \
  --identity /home/manuel/.ssh/zero-five-media-relay \
  --item relay-manifest-test.txt \
  --destination /home/manuel/services/media-pull/staging
```

The client accepts only safe top-level basenames. Names containing `/`, `..`, spaces, or shell metacharacters are rejected by the relay. For every requested item, the relay requires both:

```text
<item>
<item>.manifest
```

The relay streams the selected pair, not the entire outbox.

## Pull a folder

A clean folder can be selected using its top-level name. The scanner creates one
companion manifest for the folder, containing hashes for every regular file recursively
below it. The folder structure is preserved at the destination:

```bash
media-pull \
  --delta 10.8.0.2 \
  --identity ~/.ssh/zero-five-media-relay \
  --item movies \
  --destination /chosen/folder
```

The result is placed under the destination with its relative structure, for example:

```text
/chosen/folder/movies/
/chosen/folder/movies/2026/title.mkv
/chosen/folder/movies.manifest
```

The client verifies every hash in the folder manifest after extraction. A folder with a
missing manifest, a malformed manifest, a symlink, or a hash mismatch is rejected.

Selectors are top-level names using letters, numbers, `.`, `_`, and `-`. Absolute paths,
path separators, `..`, shell metacharacters, and symlink escapes are rejected. Selecting a
nested subfolder directly is not currently supported; select its top-level parent folder.

## Pull several selected files or folders
```bash
media-pull \
  --delta 10.8.0.2 \
  --identity /home/manuel/.ssh/zero-five-media-relay \
  --item movie-one.mkv \
  --item movie-two.mp4 \
  --destination /chosen/folder
```

With no `--item`, the client retains an all-eligible-items mode:

```bash
media-pull \
  --delta 10.8.0.2 \
  --identity /home/manuel/.ssh/zero-five-media-relay \
  --destination /chosen/folder
```

The all-items mode still transfers only the outbox contents and still requires manifests on the destination before reporting success.

## NAS destination test

The destination is not hard-coded. If the NAS media share is mounted on Delta, first identify the actual mounted path:

```bash
findmnt -t cifs,nfs4,nfs,fuse.sshfs
mount | grep -E 'cifs|nfs|sshfs'
```

Do not guess the NAS path. Confirm that the chosen directory is mounted and writable, then run a selected pull into it:

```bash
media-pull \
  --delta 10.8.0.2 \
  --identity /home/manuel/.ssh/zero-five-media-relay \
  --item relay-manifest-test.txt \
  --destination /actual/mounted/nas/media
```

Expected successful output has this form:

```text
MEDIA_PULL_VERIFIED destination=/actual/mounted/nas/media manifests=1
```

The client first extracts into a temporary hidden receive directory beneath the selected
destination. It verifies only that newly received tree, so unrelated existing NAS metadata
such as `.DS_Store` does not cause a false failure. After verification it publishes the
selected item and its manifest into the destination. It refuses to overwrite an existing
selected file or folder.

For a real media test, use `--list`, choose one item, pull it to a temporary NAS test directory first, inspect it, and only then decide whether to place a future item in the final media directory. The current source remains on media-vm after every successful pull.

If the NAS is mounted on another enrolled computer rather than Delta, run `media-pull` on that computer with its own enrolled client key and local NAS mount path. Client keys are device-specific.

## How the relay works

### Destination to Delta

The destination client opens SSH to Delta as `media-relay`. The client's public key is stored in Delta's managed authorization file with:

```text
forced command
restrict
no-agent-forwarding
no-port-forwarding
no-X11-forwarding
no-pty
```

The client sends a small request over standard input:

```text
LIST
PULL
PULL:item-one,item-two
```

The destination never sends a source path. The relay validates the request and the item basenames.

### Delta's privileged relay wrapper

The `media-relay` login account cannot read the upstream private key, the pinned media-vm host-key file, or root-owned relay state. Its forced command invokes exactly one `sudo -n` root wrapper. Delta's sudoers policy allows only that wrapper.

The root wrapper:

1. reads and validates the request;
2. creates a temporary staging directory;
3. uses the Delta-held upstream Ed25519 key;
4. uses Delta's pinned media-vm `known_hosts` file with strict checking;
5. pulls the media-vm outbox through read-only rsync;
6. refuses source symlinks;
7. lists only manifest-backed items for `LIST`;
8. emits only requested item-plus-manifest pairs for selective pulls;
9. emits a tar stream to the destination client;
10. removes its temporary staging directory on exit.

The upstream private key is never sent to the destination computer.

### Media-vm restricted account

The media-vm account is `media-outbox`. It has:

- public-key-only SSH authentication;
- an explicit external `AuthorizedKeysFile`;
- a forced read-only `rrsync` command;
- no password login;
- no TTY;
- no TCP forwarding;
- no X11 forwarding;
- no agent forwarding;
- read and traversal ACLs only for the outbox path;
- no access to quarantine, rejected files, downloads, reports, or unrelated VM paths;
- no outbound connection to Delta or any destination.

The account uses `/bin/sh` only so OpenSSH can start the forced command. That is not an interactive access grant: all authorized keys carry the forced `rrsync` command and SSH restrictions.

## Pipeline before the pull

```text
qBittorrent complete/
Firefox and Tor Browser browser-inbox/
        ↓
stable-item check
        ↓
quarantine/
        ↓
PrivateNetwork scanner service
        ↓
ClamAV + YARA + file type + ffprobe + SHA-256
        ↓
clean item → outbox/ plus item.manifest
problematic item → rejected/ and private report
```

The pipeline is operated by these installed components:

```text
/usr/local/libexec/media-pipeline-process-complete
/usr/local/libexec/media-pipeline-scan-item
/etc/systemd/system/media-pipeline-process-complete.service
/etc/systemd/system/media-pipeline-process-complete.path
/etc/systemd/system/media-pipeline-process-complete.timer
```

The path watcher handles normal arrivals. The two-minute timer is the recovery mechanism if a filesystem event is missed. Processing uses a lock and waits for the top-level item to remain stable before moving it into quarantine.

The scanner runs as `zero` in a systemd sandbox with `PrivateNetwork=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`, and write access limited to the media pipeline tree. It does not execute submitted media or scripts.

A clean item receives a companion manifest in `outbox/` named:

```text
<item>.manifest
```

The manifest records the format, item name, clean verdict, UTC completion time, scanner versions, and SHA-256 lines for every regular file. The manifest receives an explicit read ACL for `media-outbox`; default ACLs alone are insufficient because the manifest is generated in a private report directory and then moved into `outbox/`.

## Destination verification

After extraction, `media-pull` requires at least one manifest. It rejects any top-level non-manifest item that has no matching companion manifest. It then checks every manifest for:

```text
verdict=clean
valid manifest structure
at least one hash line
matching SHA-256 values for received files
```

A failed SSH connection, interrupted tar stream, missing manifest, malformed manifest, extra unmanifested file, or hash mismatch returns non-zero. The source outbox is never deleted automatically.

The destination folder should preferably be empty or dedicated to this transfer. If it already contains unrelated unmanifested files, the client will reject the result rather than silently treating those files as verified.

## Enrollment of another computer

Each destination computer needs its own Ed25519 client key. The private key stays on that computer. Only its public key is copied to Delta and enrolled with the Delta helper.

On the new destination:

```bash
umask 077
ssh-keygen -t ed25519 \
  -f ~/.ssh/zero-five-media-relay \
  -C destination-media-relay
```

Copy only the `.pub` file to Delta, then on Delta run:

```bash
sudo bash /tmp/enroll-media-relay-client.sh \
  destination-name \
  /path/to/destination-public-key.pub
```

Install the same `media-pull` command on the destination and use its private key with `--identity`. Enrollment is explicit; an arbitrary LAN or VPN computer cannot use the relay.

To remove a client, remove its named public-key line from Delta's managed authorization file using an audited administrative change, validate the SSH configuration, and reload SSH. Do not delete the upstream key when removing a destination client.

## Failure interpretation

```text
Host key verification failed
```

Check the relevant pinned host-key file and compare fingerprints before changing it. Never disable strict checking as a workaround.

```text
Permission denied (publickey)
```

Check the target host's SSH journal, the effective `AuthorizedKeysFile`, the public-key fingerprint, and the permissions/traversal of the external key file. A root-run test can pass while the real forced account fails.

```text
mktemp: Permission denied
```

The relay staging directory is not writable by the execution identity. The root wrapper design should keep the staging directory root-owned and run the wrapper through its exact sudo rule.

```text
No manifests received; refusing success.
```

The source either has no clean published manifest or the relay did not transfer one. Do not broaden the relay to scan reports. Fix the clean-output publication step.

```text
Unmanifested item received
```

The destination contains a file without its companion manifest. Stop and investigate; do not import it.

```text
Manifest verification failed
```

Do not import the file. Preserve the source, inspect the destination filesystem and transfer path, and repeat only after the cause is understood.

A `tar` error following an SSH error is normally a downstream symptom of the SSH failure, not an independent archive diagnosis.

## Rollback and cleanup

A pull does not modify or delete the media-vm source. To remove only the Delta command, delete the installed user command:

```bash
rm -f ~/.local/bin/media-pull
```

To disable a destination client, remove only that client's authorization entry on Delta and reload SSH. Keep the upstream key and media-vm account if the relay is still used by other enrolled destinations.

To remove the entire relay deployment, first disable destination authorization, then remove the Delta relay configuration and sudoers entry, and finally remove the media-vm restricted account and its narrow firewall rule. Preserve evidence and verify that no unrelated SSH or WireGuard configuration was changed.

## Current limitations

- The one-VM quarantine design is operational containment, not an independent malware-analysis trust boundary.
- The relay trusts Delta as a high-value key-management and transport point.
- Manifests are integrity metadata with SHA-256; they are not signed attestations.
- Source cleanup and ACK ordering are not automated.
- The final Gamma Jellyfin library path is not yet documented or enabled.
- A separate quarantine VM with an independent signing key remains the stronger future design.
- The harmless Delta test fixture proves transport and verification, not media-library import behavior.

title: Home App Gateway (Traefik on Delta)
description: "Traefik v2.11 reverse proxy on Delta routes private app names (proxmox.zero-five.space etc.) to LAN backends on Beta/Gamma — DNS-only names via AdGuard, no client peer changes."
---

Delta runs a private reverse proxy (**Traefik v2.11**) that routes home app
names to LAN/mesh backends. Names are private AdGuard rewrites → Delta's mesh
IP; Traefik terminates TLS and forwards by `Host` header to the machine that
actually runs the app (Beta, Gamma, …). Clients only ever need Delta
(`10.40.0.2`) in their WireGuard `AllowedIPs` — **no new peers per app**.

Deployed 2026-08-22, following the AdGuard Home deploy on Delta.

## The model

```
name.zero-five.space ──► AdGuard rewrite → 10.40.0.2 (Delta)
                              │
                              ▼
                     Traefik :443 on Delta (terminates TLS, *.zero-five.space cert)
                              │  Host: name.zero-five.space
                              ▼
                     LAN backend (e.g. https://192.168.1.166:8006 Proxmox)
```

Why this design (user decisions, 2026-08-22):

- **Names stay private — NOT in Cloudflare.** The user explicitly does not
  want every home app name enumerated in public DNS. AdGuard rewrites keep
  them Zone-2 only. (An alternative — grey-cloud Cloudflare A records like
  the Alpha VPN-only pattern — was offered and rejected for home names.)
- **No new peers on clients.** Every client already reaches `10.40.0.2`
  (Delta). Traefik does the LAN hop, so adding an app never touches client
  WireGuard configs.
- **Traefik v2.11** — matches the Alpha hub conventions (do NOT bump to v3;
  the Docker provider API mismatch and the file-provider patterns are proven).
  Caddy was considered (lighter, auto internal CA) but consistency won.

**PITFALL — port binding vs host mode.** The original layout published `ports:`
only on `10.40.0.2` + `192.168.1.106`. That changed 2026-08-23: **host `network_mode`
drops the `ports:` block entirely** (it binds `:80`/`:443` on all host IPs), which is what
lets Traefik reach the LAN router at `192.168.1.1:80` and host services directly —
the container→host/→LAN bridge isolation made LAN backends unreachable otherwise. VPN-only
enforcement is done by the **route middleware** (`ipWhitelist 10.40.0.0/24`), not by the
bind address. See `references/router-access-and-container-egress.md`.

## Dual-cert: Let's Encrypt primary + internal-CA fallback

Delta serves **two certificate layers** (deployed 2026-08-22):

1. **Let's Encrypt (primary)** — per-name certs issued by **certbot** on Delta
   via Cloudflare DNS-01 (TXT record, never exposes app names in A records).
   Trusted by every browser/OS — zero device setup for public trust.
2. **Internal CA (fallback)** — `Zero Five Internal CA` wildcard as
   Traefik's **default certificate**. Served automatically only when the LE
   cert for a name is missing/expired (e.g. Cloudflare unreachable at
   renewal). Devices that installed the CA stay green during outages.

**Why certbot and not Traefik's ACME?** Traefik v2.11's ACME provider skips
issuance for any domain covered by a store cert — and a wildcard internal-CA
cert covers *every* subdomain, so Traefik ACME **never fires** alongside a
fallback cert (verified in source: `certificate_store.go` GetAllDomains
includes the default cert's domains). Running certbot externally sidesteps
that: LE certs land as static files in `tls.certificates` (exact SNI match
wins), the internal CA lives in `tls.stores.default.defaultCertificate`
(served only when no dynamic cert matches — `tlsmanager.go` line ~220).

**Renewal:** `certbot.timer` runs twice daily; renews ~30 days before expiry.
Deploy hook `/etc/letsencrypt/renewal-hooks/deploy/zero-five.sh` copies
renewed certs to `/home/manuel/services/proxy/certs/le/` and touches
`dynamic/reload-trigger.yml` to reload Traefik. On renewal failure the old LE
cert keeps serving; only a *prolonged* Cloudflare outage (past expiry)
triggers the internal-CA fallback.

**CA files (Delta, root-owned):**
- Private key: `/home/manuel/services/proxy/ca/ca.key` (mode 600, never leaves Delta)
- Public cert: `/home/manuel/services/proxy/ca/ca.pem` (distributed via `proxy/zero-five-ca.pem` in the infra repo)
- Wildcard leaf: `/home/manuel/services/proxy/certs/zero-five.pem` (signed by CA)
- **Fullchain** (default cert): `/home/manuel/services/proxy/certs/zero-five-fullchain.pem`
- LE certs: `/etc/letsencrypt/live/<name>/` + copies in `/home/manuel/services/proxy/certs/le/`

**Backup is critical:** the CA key is the single point of failure — losing it
forces every device to re-trust a new CA. `/home/manuel/services/proxy` is in
`delta-paths` (added 2026-08-22); verify the 21:00 backup actually covers it.
Full rebuild runbook: [Delta Rebuild & Recovery](/docs/raspberry/delta-rebuild).

### How to trust a device (one-time)

- **macOS (MacBook)**: `sudo security add-trusted-cert -d -r trustRoot -k
  /Library/Keychains/System.keychain zero-five-ca.pem` (or double-click →
  Keychain Access → Always Trust)
- **iOS (iPhone)**: send `zero-five-ca.pem` to the phone (AirDrop/Mail) →
  install profile → Settings → General → About → Certificate Trust Settings
  → enable full trust for "Zero Five Internal CA"
- **Linux**: copy to `/usr/local/share/ca-certificates/zero-five-ca.crt` →
  `sudo update-ca-certificates`

Fetch the cert from the infra repo: `curl -O https://raw.githubusercontent.com/Manuel0516/zero-five-infra/main/proxy/zero-five-ca.pem` (or `scp manuel@10.40.0.2:/home/manuel/services/zero-five-infra/proxy/zero-five-ca.pem .`).

**PITFALL — serve the full chain.** Traefik's dynamic TLS must point at a
**fullchain** file (leaf + CA concatenated), not just the leaf. With only the
leaf, browsers report `SEC_ERROR_UNKNOWN_ISSUER` even after the CA is
installed ("the site isn't sending intermediate certificates we trust").
Build it once: `cat certs/zero-five.pem ca/ca.pem >
certs/zero-five-fullchain.pem` and reference `/certs/zero-five-fullchain.pem`
in the routes' `tls.certificates`. Verified 2026-08-22: fullchain serves 2
certs, subjects leaf + CA.

### The router route (`dynamic/router.yml`) — the one that needs its LE cert

The `router` route exists to reach the home router's admin UI from behind the VPN. Two
details make it special and both were resolved 2026-08-23:

1. **Backend is the host-mode direct router**, `http://192.168.1.1:80` — reachable
   directly since Traefik runs in host `network_mode`. (The older `router-forwarder.py`
   host-side forwarder on `:2080` was the pre-host-mode workaround and is still
   installed as a fallback, but the route no longer points at it.)
2. **It needs its own per-name LE cert in the route's `tls.certificates`.** Without the
   `tls.certificates:` block, Traefik serves the **internal-CA wildcard** for this SNI.
   On a phone/roaming device that never installed the Zero Five CA, the browser hard-
   blocks the untrusted cert → presents as "address not being served / can't reach over
   VPN," identical to the `dns` route's earlier symptom. The fix is exactly the dual-cert
   pattern: add a per-name LE cert and reload. Current routed `router.yml` has it:

```yaml
tls:
  certificates:
    - certFile: /certs/le/router.zero-five.space.pem
      keyFile: /certs/le/router.zero-five.space-key.pem
```

   Re-verify the **issuer** is Let's Encrypt, not `Zero Five Internal CA`, with:
   `openssl s_client -connect 10.40.0.2:443 -servername router.zero-five.space` → issuer
   `O=Let's Encrypt`. Diagnosis ordering for any "can't reach `<name>` over VPN" report:
   (a) AdGuard rewrite → `10.40.0.2`, (b) Traefik serves the route from alpha (`curl
   --resolve`, 200/302), (c) **the cert issuer for that SNI** — before touching
   redirects or proxying.

## Adding an app (the pattern)

1. **AdGuard rewrite** (Settings → DNS rewrites, or yaml): `app.zero-five.space
   → 10.40.0.2`
2. **Traefik route** in `dynamic/<app>.yml` — for an HTTPS LAN backend with a
   self-signed cert (Proxmox, Jellyfin, …) use the `lan-selfsigned`
   transport:

```yaml
http:
  serversTransports:
    lan-selfsigned:          # define once, reuse per app
      insecureSkipVerify: true

  routers:
    <app>:
      rule: "Host(`app.zero-five.space`)"
      entryPoints: [websecure]
      service: <app>
      tls: {}

  services:
    <app>:
      loadBalancer:
        serversTransport: lan-selfsigned
        servers:
          - url: "https://192.168.1.XXX:PORT"
```

3. **Wire the per-name LE cert into the route** — **required**, not optional, or roaming
   devices without the internal CA can't load it. Two parts:
   - Issue the LE cert (certbot, Cloudflare DNS-01):
     ```bash
     sudo certbot certonly --dns-cloudflare \
       --dns-cloudflare-credentials /etc/letsencrypt/cloudflare.ini \
       -d app.zero-five.space --cert-name app.zero-five.space \
       --non-interactive --agree-tos --email manuellore05@gmail.com \
       --preferred-challenges dns-01 --key-type ecdsa
     ```
     The deploy hook copies it to `certs/le/` automatically (fix the hook's
     `for name in ...` list to include the new name or the copy never happens — the
     classic "exact-SNI fallback" bug).
   - Add the `tls.certificates:` block to `dynamic/<app>.yml` referencing those files
     (matches `dns.yml` / `proxmox.yml` / `router.yml`). Only the internal-CA wildcard
     covers the name *while the LE cert is being issued*, and only devices that trust
     the Zero Five CA will load it.
4. `sudo docker compose -f /home/manuel/services/proxy/compose.yaml restart`
   (dynamic files hot-reload, but a restart guarantees pickup) — actually
   only needed if the static config changed; `dynamic/` files are watched.
   A `touch dynamic/reload-trigger.yml` is enough for file changes.

## Verification (from alpha, no dig needed)

```bash
# DNS rewrite:
python3 <raw-socket query for proxmox.zero-five.space via 10.40.0.2> → 10.40.0.2
# TLS + route:
curl -sk --resolve proxmox.zero-five.space:443:10.40.0.2 https://proxmox.zero-five.space/ -o /dev/null -w '%{http_code}'   # 200
# title check:
curl -sk https://10.40.0.2:443/ -H "Host: proxmox.zero-five.space" | grep -o '<title>[^<]*</title>'
# which cert layer is serving (LE vs internal CA):
echo | openssl s_client -connect 10.40.0.2:443 -servername proxmox.zero-five.space 2>/dev/null | grep issuer
#   → O=Let's Encrypt (primary) or CN=Zero Five Internal CA (fallback)
```

## Automatic DNS adoption (router DHCP — the "no per-device config" path)

The user wants AdGuard DNS **without touching each device**. The clean way on
the LAN is the **router's DHCP server**: point it at Delta's LAN address as
the DNS server, and every device that joins the network (phone, laptop, TV,
NAS…) receives AdGuard automatically — no per-device settings.

On the home router (192.168.1.1 admin UI), set:

- **DHCP / DNS server → `192.168.1.106`** (Delta's LAN IP; static/reserved)

Then all LAN clients resolve private names (`proxmox.zero-five.space`, …) and
get ad-blocking out of the box.

**Resilience — always pair with a fallback.** A single DNS server is a SPOF:
if Delta is down, clients lose resolution (looks like losing internet).
Configure a **secondary DNS** on every path:

- WG configs: `DNS = 10.40.0.2, 1.1.1.1` (try AdGuard, fall back to Cloudflare)
- Router DHCP: primary `192.168.1.106`, secondary `192.168.1.1` (or `1.1.1.1`)

Applied 2026-08-22: MacBook + iPhone WG configs use
`DNS = 10.40.0.2, 1.1.1.1`. Private names only resolve when Delta is up
(unavoidable — only AdGuard knows them); public internet keeps working during
an outage via the fallback (after a short resolution delay).
